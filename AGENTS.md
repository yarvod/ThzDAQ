# Repository Guidelines

## Project Structure & Module Organization

ThzDAQ is a uv workspace for SIS mixer control and measurements; see `docs/architecture.md` for the design and `docs/backlog.md` for ideas not taken up yet.

- `packages/thzdaq-instruments` (`thzdaq_instruments`): capability interfaces, quantities (readable/settable values with units derived from capabilities) and actions (what a device does on request, declared the same way), kept state (what only the program knows of an instrument, told on every change and given back when it opens: `state.py`; a grid counts its angle, `angle.py`), fixed channels and sub-device types of instruments, transports (TCP, serial, Prologix, VISA, HTTP, Modbus) with a shared pool and per-link locks, a connection as one line (`parse_connection`: `tcp://host:port`), instrument drivers in `drivers/` (generic ones, type `generic`, only reach an instrument without a driver: raw commands, `drivers/generic.py`), simulators in `sim/`, driver registry. No Qt, no numpy.
- `packages/thzdaq-core` (`thzdaq_core`), in layers: `domain/` (station profiles with instruments and their configured devices, device kinds, the safety section and the guarded ports every device is handed out in, in `station/`; procedures with device slots, plots and the catalog in `measurements/`, the bench's own measurements as procedures in `measurements/custom.py`; the measurement DTO in `data/`; SIS tools in `sis/`), `application/` (the runner and its ports; `procedures.py` the catalog of built-in and own measurements, `custom.py` the library described and its runs: a session the script's process takes over), `adapters/` (JSON measurements: a running one is its description, its records appended to `<id>_<procedure>.jsonl` next to it, whole at its end; YAML profiles, each save keeping the previous version in `.history/` next to it; legacy `settings.ini`; `instrument_states.py`: what the daemon keeps of instruments, `state.json` (`state-sim.json`) next to `daemon.json`, given back to an instrument as it opens by `application/kept.py`; `library.py`: the library `measurements/` of the program, a script described by its process), `cli/` (`thzdaq-station`: profiles as files, without the daemon). No Qt.
- `packages/thzdaq-analysis` (`thzdaq_analysis`): pure calculations on measured data (I-V analysis, noise temperature, shot noise, 2SB sideband rejection, decibels); arrays and numbers in, results out; depends only on numpy.
- `packages/thzdaq-api` (`thzdaq_api`): the daemon's contract (operations by area, DTO, events, errors, `catalog.py`) and its client: `RemoteLab` (HTTP + SSE, `remote.py`), the daemon's files and `connect_or_start()` (`host.py`); workspaces (`workspace.py`: `thzdaq.toml`, the workspace found up from here, the profile it expects); the client of scripts: `connect()`, the CLI's commands as functions, device objects and runs (`lab.py`); the bench's own measurements (Custom): a script with declarations `device`, `value`, `plot`, `instrument` at its top (`custom.py`: the contract, names by AST; `declare.py`: the declarations; `raw.py`: an instrument a script declares, its raw commands named by `reading` and `setting`; `declaring.py`: how this process's script runs — described, given inputs, or as it is), examples of them (`examples.py`, the scripts themselves in `examples/`, data of the package that run on the simulators); windows a client opens as programs of their own: the main window in a workspace and the plots window of a measurement (`windows.py`), a script's own measurement `lab.measurement` (`script.py`; its operations in `sessions.py`, asked in the script's terminal by `terminal.py`); scripts the daemon runs and what they are allowed in advance (`scripts.py`).
- `packages/thzdaq-daemon` (`thzdaq_daemon`): the bench daemon: composition root (`compose.py`), HTTP + SSE over the dispatcher (`server.py`), the process with its lock, host file, idle timeout and restart (`process.py`).
- `packages/thzdaq-cli` (`thzdaq_cli`): the command `thzdaq`, a client of the daemon as the GUI is (`daemon …`, `serve`, `devices`, `read`, `set`, `call`, `raw`, `safe`, `connections`, `procedures`, `describe`, `run`, `status`, `measurements`, `cancel`, `watch`, `plot`, `show`, `station`, `approvals`, `script …`, `run-script`, `mcp`, `agent-setup`, `init`, `gui`; `--json`, `--yes`, `--simulate`; arguments after `--` go to the script; commands work in the workspace found up from the current folder); `packages/thzdaq`: the PyPI meta-package.
- `packages/thzdaq-mcp` (`thzdaq_mcp`): `thzdaq mcp`, the bench's tools for agents (Claude Code, Codex) over MCP stdio on the `mcp` SDK: a client of the daemon as `mcp:<agent>`; tools are operations of `thzdaq_api.catalog` (`tools.py`), answers short text with units (`present.py`), resources (`resources.py`). The command line finds it by the entry point `thzdaq.cli`, never by import. The guides agents read (`AGENTS.md` of a workspace, `thzdaq://guide/<topic>`) are package data of `thzdaq_api` (`assistant/*.md`, `guides.py`).
- `packages/thzdaq-gui` (`thzdaq_gui`): PySide6 + PySide6-QtAds + pyqtgraph application in the layout of the old app: the window only assembles the parts (`main_window.py`), docks by name and where they open (`docking.py`, names in `dock_names.py`), graph and device docks that follow the graphs and the station (`graph_docks.py`, `device_docks.py`), perspectives (`perspectives.py`), docks (`docks/`: Setup, device docks with raw commands to the instrument in a folded Advanced section (`raw.py`), measurement docks, Data, Log, Processes: what runs now, `processes.py`), graph docks (`graphs.py`; runs started by other clients reach them through `run_graphs.py`), dock search (`navigator.py`: menus as a searchable tree by type, Ctrl+K), Lite and Pro modes (`modes.py`; Lite: one layout and the run bar on top, `runbar.py`; Pro: a dock per measurement and perspectives), run controls as a view of a run's status (`run_controls.py`), file dialogs that remember their folder (`folders.py`), the window's workspace and its File menu (`workspace.py`, `workspace_menu.py`), VS Code for a folder, a script or a line of it (`external_editor.py`), the bench's own measurements: their docks follow the catalog (`measure_docks.py`; `docks/custom.py`: Code, where each declared plot goes, what the script printed), a dock per script's file (`code_docks.py`, `docks/code.py`: the editor `editor.py` with line numbers, pygments, jedi and the bench's completions, Save, Check, Run, pieces to insert, changes from disk, the script a measurement kept from Data; its model `models/code.py`), what a script printed (`script_output.py`), dark theme with orange accents and qtawesome icons (`theme.py`). The GUI is a client of the daemon: the session works with a `Lab` (`connect_or_start()` in the app, a `LocalLab` in tests), view models in `models/` (run, device, daemon, scripts the daemon runs, a script's file; `runs.py` routes each run's events to one run model, the runs of other clients too) call it, the Daemon dock (`docks/daemon.py`) shows and controls the daemon. With `--plot <id|file>` the program is only the plots window of one measurement (`viewer.py`: its snapshot, then its events, or a file).
- `stations/`: bench profiles (YAML, version 2: instruments with `devices`; ids name the kind of device, e.g. `power_supply_3`). `main.py` is the GUI entry point, and with `--serve` the daemon a built program's clients start; `cli_main.py` is the entry point of the built `thzdaq-cli`. `assets/` holds the pixel app icon (`thzdaq.ico`, `thzdaq.icns`, drawn by `assets/make_icon.py`; rerun it after changing the drawing). `firmware/` keeps device firmware (Arduino grid rotators).

Dependencies point one way: clients (gui, cli, mcp) → api ← core → instruments and core → analysis; the daemon → core and api. `uv run lint-imports` checks the boundaries (contracts in the root `pyproject.toml`).

## Architecture Rules — Required

Fix the design, not the symptom. A change that only works with a hack is not done: restructure, or stop and ask.

- **One-way dependencies, no cycles.** Between packages gui → core → instruments; inside the GUI the entry point (`app.py`) → the windows (`main_window.py`, it only assembles; the plots window `viewer.py`) → their parts (`docking.py`, `graph_docks.py`, `device_docks.py`, `perspectives.py`, `modes.py`, `runbar.py`, `run_graphs.py`) → docks (`docks/`) → widgets and view models (`forms.py`, `run_controls.py`, `collapsible.py`) → `theme.py`, `settings.py`, `dock_names.py`. A lower module never imports a higher one; it tells through Qt signals or callbacks it is given.
- **One owner per responsibility.** New behaviour goes into the object that owns the concept, not into `MainWindow` or into a widget that happens to be near. A concept lives in one place (dock names in `dock_names.py`, dialog folders in `folders.py`, a run's state in `RunStatus`); never parse or rebuild it elsewhere.
- **Polymorphism over branching.** What differs by mode, kind or device is an object asked for its answer (`Mode.dock_of`, capability interfaces), not `if mode == …` / `isinstance` chains spread over callers.
- **State in models, widgets are views.** Widgets show a model and call its methods; they never read another widget's labels, buttons or progress bars to learn state.
- **No hacks.** No flags that silence a path for one caller, no sleeps or timers to "let it settle", no retries, no `getattr(self, "_x", default)` for attributes that may not exist, no catch-all `except` to hide a failure, no dead code left behind. If a third-party library (Qt, ADS, pyqtgraph) needs a workaround, it lives in the module that wraps that library (ADS: `docking.py`), runs once at the point where the library's behaviour causes the problem, and its comment names that behaviour.
- **Prove it.** A bug fix reproduces the bug first (a test, or a script on simulators) and checks the fix against it.

### Target boundaries (daemon work, `docs/daemon.md` → «Пакеты, слои и границы»)

New code follows these boundaries now; existing code moves there during milestone M1.

- **Packages.** `thzdaq-api` (contract and client: operations, DTO, events, errors, the measurement file format, `RemoteLab`, `connect_or_start`; depends only on `msgspec`) ← `thzdaq-core` (domain and use cases) → `thzdaq-instruments` and `thzdaq-analysis` (pure calculations, numpy only, imports no ThzDAQ package); `thzdaq-daemon` (process, HTTP + SSE, the server-side composition root) → core and api. Clients `thzdaq-gui`, `thzdaq-cli`, `thzdaq-mcp` import only `thzdaq_api`, never `thzdaq_core`, `thzdaq_instruments`, `thzdaq_analysis` (analysis is a daemon operation; scripts and notebooks may import it) or `thzdaq_daemon`. `thzdaq` is the PyPI meta-package with extras. Only the root `main.py` knows both the GUI and the daemon.
- **Layers in core.** `domain/` (station, `GuardedPort`, procedures, parameters, plots, measurement, leases) ← `application/` (handlers, dispatcher, policy, approvals, runner, events, lanes, polling, scripts, workspaces, ports, `LocalLab`) ← `adapters/` (JSON store, YAML profiles, journal). The domain touches no files or clocks and starts no threads; it gets them through ports and the run context.
- **Use cases.** One operation = one Struct of arguments in its area module of `thzdaq_api` (`devices.py`, `measurements.py`, `station.py`, ...), listed in `catalog.py`, and one stateless handler class in `thzdaq_core/application/handlers/<area>.py`, registered by the explicit list in `application/assembly.py`. Every call from outside goes through the dispatcher: arguments → handler → events (policy comes with rights, milestone M2). A manual write checks the leases just before writing. Procedures inside the daemon talk to their devices directly, not through the dispatcher.
- **Contract types.** DTO, operation arguments and events are `msgspec` Structs in `thzdaq-api`; JSON schemas are generated from them, never written by hand. Values with units travel as strings and are parsed once, by the daemon.
- **GUI.** View models in `thzdaq_gui/models/` are QObjects on QtCore that call `Lab`; they never import QtWidgets. Widgets show a view model and call its methods. One bridge turns `RemoteLab` events into Qt signals. Forms come from `ProcedureInfo` schemas, graphs from `PlotInfo`, analysis from daemon operations.
- **Vocabulary.** Quantity keys and units live in instruments, a procedure's name, slots and plots on its class, shared procedure parameters and axis labels in `domain/measurements/procedures/common.py`, operation names, event types and error codes in api, GUI settings keys in one GUI module. Use them by import; `tests/test_architecture.py` fails on a function body, a phrase shown to people or a dotted/slashed identifier written in two modules (a phrase that only looks the same goes into its `ALLOWED` with the reason).
- **Enforcement.** import-linter contracts in the root `pyproject.toml` run in pre-commit and CI next to the duplicate test; a broken boundary fails the build.

## Build, Test, and Development Commands

- `uv sync` creates or updates `.venv`; `uv lock` after changing any `pyproject.toml`.
- `uv run python main.py --station stations/2sb.example.yaml --simulate` runs the GUI on simulators.
- `uv run thzdaq [--simulate] run <procedure> [--device slot=device] [--set name=value]` runs a measurement in the daemon and follows it (parameters typed as `describe` shows them, a sweep `start:stop:points`); `uv run thzdaq procedures` / `describe <procedure>` show what exists; the daemon loads a profile with `thzdaq daemon start --station <profile>` or `thzdaq station load <profile>`.
- `uv run thzdaq [--simulate] script start <file.py> [--allow set:<device>|raw:<instrument>] [-- args]` runs a script in the daemon apart from the terminal (`script list|logs <id> [-f]|stop <id>`); `python <file.py>` with `from thzdaq import connect` runs it in the terminal. A script has the rights of whoever started it: a person's changes the bench as the person would in a dock (what a dock confirms is asked), an agent's (`CLAUDECODE`, `CODEX_SANDBOX…`, `THZDAQ_AGENT` in its environment; `script:agent:<name>`) asks as the agent does, and an agent's `--allow` allows nothing.
- `uv run thzdaq [--simulate] raw <instrument> "<command>" [--answer] [--share]` sends an instrument a command its driver does not wrap (`lab.raw` in Python, Advanced in its dock): a query (with `?`) answers; a write, which no limit checks, is confirmed by a person (`--yes`), needs `--allow raw:<instrument>` or a person's yes in a person's script (within a measurement the yes holds until it ends), and is refused to agents and their scripts; the devices on the instrument are read again after it. An instrument without a driver: `instrument("gauge_1", driver="generic.scpi", connection="tcp://…", x=reading(...), y=setting(...))` at the top of a script puts it into the profile once a person allows it (Setup → Add instrument → Generic (raw) does it by hand).
- `uv run thzdaq [--simulate] plot <id|file> [--table T --x X --y Y [--group G]]` opens the plots of a measurement in a window of their own (`lab.plot`, `run.show()`, `m.show()` in Python), apart from the terminal.
- `uv run thzdaq init [<folder>] [--station <name>] [--agents]` makes a workspace (`thzdaq.toml`, `data/`, `scripts/`); commands run in it or below it measure there, and `uv run thzdaq gui` opens the window in it.
- `uv run thzdaq [--simulate] agent-setup <folder>` lets Claude Code and Codex measure in a folder: `.mcp.json`, `.codex/config.toml` (trusted projects) and `AGENTS.md` for them; they start `thzdaq mcp` by its absolute path.
- `uv run thzdaq-station check <profile> --simulate` checks a bench profile as a file, without the daemon.
- `uv run thzdaq-daemon --station <profile> [--simulate] [--idle-timeout 0]` runs the bench daemon in the terminal; clients start it themselves through `thzdaq_api.host.connect_or_start()` (its log: `thzdaq[-sim]-daemon.log` in the temp folder).
- `uv run pytest` runs all package tests (GUI tests run offscreen); `uv run pytest packages/thzdaq-core` for one package.
- `sh build.sh` / `build.bat [name]` build the PyInstaller distribution into `dist/` from `ThzDAQ.spec`: `ThzDAQ` (windowed: the GUI, `--serve` the daemon) and `thzdaq-cli` (console) over one `_internal`; the release smoke test starts, asks and stops the build's daemon with `thzdaq-cli`.
- `uvx pre-commit run --all-files` runs Black, autoflake, hygiene hooks and `lint-imports` before committing; `uv run lint-imports` checks the architecture boundaries alone.
- `uv run python release.py X.Y.Z` (or `X.Y.Z-beta.N`: a pre-release on GitHub and PyPI, a new number for every beta) stamps one version on the program (`thzdaq_gui/version.py`, as the tag spells it) and on every package in `packages/` (PEP 440, `X.Y.ZbN`; the packages require each other at exactly it), runs `uv lock`, tags `vX.Y.Z` and pushes (`--again` moves an existing tag to the current commit after fixes and builds it again; PyPI keeps the packages it got first). `.github/workflows/release.yml` then tests, builds the Windows x64 zip and publishes the GitHub release that Help → Check for updates installs (`thzdaq_gui/updates.py`, standalone `thzdaq_gui/updater.py` built as `updater.exe`); its `packages` job builds and checks the packages, its `pypi` job publishes them by trusted publishing (environment `pypi`). `.github/workflows/ci.yml` runs the tests on every push.
- PyPI packages: `thzdaq` (the client: `thzdaq-api` and `thzdaq-cli`, no numpy or drivers; extras `analysis`, `daemon`, `mcp`, `gui`, `all`) and every `thzdaq-*`, MIT (`LICENSE` copied into each package). `uv build --all-packages -o dist/packages` builds them; `uv run --package thzdaq-api python check_packages.py dist/packages` installs them as a user gets them into clean environments; `tests/test_packages.py` checks one version, exact pins and the same metadata everywhere. A new package in `packages/` gets the same metadata, a `LICENSE` copy and a pending trusted publisher on pypi.org.

## RTK (Rust Token Killer) — Required

RTK is installed and available on `PATH`. Agents must use RTK for every supported shell command by default to reduce command-output token usage. Do not run the raw equivalent unless exact unfiltered output is required, RTK does not support the command, or RTK fails. If RTK fails, fall back to the underlying command so work can continue.

Required command mappings include:

- `git status`, `git diff`, and `git log` → `rtk git status`, `rtk git diff`, and `rtk git log`.
- `git add`, `git commit`, `git push`, and `git pull` → the matching `rtk git ...` command.
- `rg` searches → `rtk rg <pattern> <path>`. Use `rtk grep` only when a `grep` binary is available on `PATH`.
- Large file reads → `rtk read <file>`.
- Directory listings and file searches → `rtk ls <path>` and `rtk find <pattern> <path>`.
- Python test runs → `rtk test uv run pytest ...`.

Run `rtk --version` to verify the installation and `rtk gain` to inspect token savings.

## Python and uv — Required

All Python environment and command interactions must go through `uv`: use `uv sync`, `uv add`/`uv remove` (with `--package <member>` for workspace packages), and `uv run ...`. Do not invoke `pip` directly or manually maintain a separate virtual environment. Keep every `pyproject.toml` and `uv.lock` committed and synchronized.

## Coding Style & Naming Conventions

Python with 4-space indentation, formatted by Black; autoflake removes unused imports. Values are SI inside the code (Hz, V, A, K, s, Pa), power in dBm, angles in degrees; display units live only in parameters and plots. New instruments implement capability interfaces (`thzdaq_instruments.capabilities`), declare their passport (`limits`) and get a simulator plus contract tests; a setpoint names the methods that set it (`Quantity.setters`) so the guard sees every call; new measurements are `Procedure` subclasses added to `BUILTIN` in `thzdaq_core/domain/measurements/procedures/__init__.py`. Keep comments short and reserve them for non-obvious hardware, timing, or UI behavior.

## Testing Guidelines

Tests live next to each package (`packages/*/tests`, `test_*.py`, pytest); `tests/` at the root checks the whole repository (architecture rules). Drivers are tested against protocol emulators on `FakeLink` and the shared capability contracts in `packages/thzdaq-instruments/tests/contracts.py`; procedures run on simulators; GUI tests run offscreen. Hardware is never needed for tests. For changes that need real instruments, document the bench and steps used.

## Commit & Pull Request Guidelines

Short imperative messages, optionally with a conventional prefix (`feat:`, `fix:`, `docs:`). Pull requests describe the affected package, list manual test steps (bench, profile, simulate or hardware), mention profile changes in `stations/`, and include screenshots for visible UI changes.

No AI attribution anywhere in the history: commit messages, tags, pull requests and release notes carry no `Co-Authored-By` trailer for an AI assistant, no "Generated with …" line and no other mention of the assistant or model. The author of every commit is the repository owner. This rule overrides any default attribution an agent or tool would add.

## Security & Configuration Tips

Do not commit credentials or machine-specific settings. Keep generated outputs (`dist/`, `build/`, `data/`, logs) out of review unless they are intentional reference artifacts.
