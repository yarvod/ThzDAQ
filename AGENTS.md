# Repository Guidelines

## Project Structure & Module Organization

ThzDAQ is a uv workspace for SIS mixer control and measurements; see `docs/architecture.md` for the design and `docs/backlog.md` for ideas not taken up yet.

- `packages/thzdaq-instruments` (`thzdaq_instruments`): capability interfaces, quantities (readable/settable values with units derived from capabilities) and actions (what a device does on request, declared the same way), kept state (what only the program knows of an instrument, told on every change and given back when it opens: `state.py`; a grid counts its angle, `angle.py`), fixed channels and sub-device types of instruments, transports (TCP, serial, Prologix, VISA, HTTP, Modbus) with a shared pool and per-link locks, a connection as one line (`parse_connection`: `tcp://host:port`), instrument drivers in `drivers/` (generic ones, type `generic`, only reach an instrument without a driver: raw commands, `drivers/generic.py`), simulators in `sim/`, driver registry. No Qt, no numpy.
- `packages/thzdaq-core` (`thzdaq_core`), in layers: `domain/` (station profiles with instruments and their configured devices, device kinds, the safety section and the guarded ports every device is handed out in, in `station/`; procedures with device slots, plots and the catalog in `measurements/`, the bench's own measurements as procedures in `measurements/custom.py`; the measurement DTO in `data/`; SIS tools in `sis/`), `application/` (the runner and its ports; `windows.py`: the windows that listen, the one a person was at last, and what agents ask of them, answered by the window through `ui_requested` and `answer_ui`; `procedures.py` the catalog of built-in and own measurements, `custom.py` the library described and its runs: a session the script's process takes over), `adapters/` (JSON measurements: a running one is its description, its records appended to `<id>_<procedure>.jsonl` next to it, whole at its end; YAML profiles, each save keeping the previous version in `.history/` next to it; legacy `settings.ini`; `instrument_states.py`: what the daemon keeps of instruments, `state.json` (`state-sim.json`) next to `daemon.json`, given back to an instrument as it opens by `application/kept.py`; `library.py`: the library `measurements/` of the program, a script described by its process), `cli/` (`thzdaq-station`: profiles as files, without the daemon). No Qt.
- `packages/thzdaq-analysis` (`thzdaq_analysis`): pure calculations on measured data (I-V analysis, noise temperature, shot noise, 2SB sideband rejection, decibels); arrays and numbers in, results out; depends only on numpy.
- `packages/thzdaq-api` (`thzdaq_api`): the daemon's contract (operations by area, DTO, events, errors, `catalog.py`) and its client: `RemoteLab` (HTTP + SSE, `remote.py`), the daemon's files and `connect_or_start()` (`host.py`); workspaces (`workspace.py`: `thzdaq.toml`, the workspace found up from here, the profile it expects, the Python of its scripts); that Python (`interpreters.py`, the one owner of the rule: the one `thzdaq.toml` names, else the program's own; the environments found: the workspace's `.venv` and those above, uv's tools, conda's; a chosen one checked: it runs, Python ≥ 3.11, `thzdaq` of exactly this program's version, `ipykernel` for a console); the client of scripts: `connect()`, the CLI's commands as functions, device objects and runs (`lab.py`); the bench's own measurements (Custom): a script with declarations `device`, `value`, `plot`, `instrument` at its top (`custom.py`: the contract, names by AST; `declare.py`: the declarations; `raw.py`: an instrument a script declares, its raw commands named by `reading` and `setting`; `declaring.py`: how this process's script runs — described, given inputs, or as it is), examples of them (`examples.py`, the scripts themselves in `examples/`, data of the package that run on the simulators); windows a client opens as programs of their own: the main window in a workspace and the plots window of a measurement (`windows.py`), a script's own measurement `lab.measurement` (`script.py`; its operations in `sessions.py`, asked in the script's terminal by `terminal.py`); scripts the daemon runs and what they are allowed in advance (`scripts.py`); the tools of agents and of the assistant in the window (`tools.py`: operations of the catalog chosen, run over one subscription, `Reach`; the assistant's UI tools bound to its own window; `present.py`: their short answers with units); what agents ask of a person's window (`ui.py`: `ui_state`, `ui_open`, `ui_fill_measurement`, `ui_highlight` to the window named or the one the person was at last, `window_id()`; a window names its id in its event stream, `RemoteLab(window=…)`); a console of the window: what the window gives its kernel (`console.py`: the command, with the Python of its workspace, the environment, the opening `from thzdaq import *`, `lab = connect()`) and the kernel itself (`kernel.py`: ipykernel with the bench's completions, run as `python -m thzdaq_api.kernel`; it calls the daemon as `console`, with the rights of a person's script).
- `packages/thzdaq-daemon` (`thzdaq_daemon`): the bench daemon: composition root (`compose.py`), HTTP + SSE over the dispatcher (`server.py`), the process with its lock, host file, idle timeout and restart (`process.py`).
- `packages/thzdaq-cli` (`thzdaq_cli`): the command `thzdaq`, a client of the daemon as the GUI is (`daemon …`, `serve`, `devices`, `read`, `set`, `call`, `raw`, `safe`, `connections`, `procedures`, `describe`, `run`, `status`, `measurements`, `cancel`, `watch`, `plot`, `show`, `station`, `approvals`, `script …`, `run-script` (a file and its arguments as `python` takes them, or `-m <module>` as `python -m`: a build runs a console's kernel so), `mcp`, `agent-setup`, `init` (`--python`), `python show|set|list` (the Python of the workspace's scripts), `gui`; `--json`, `--yes`, `--simulate`; arguments after `--` go to the script; commands work in the workspace found up from the current folder); `packages/thzdaq`: the PyPI meta-package.
- `packages/thzdaq-mcp` (`thzdaq_mcp`): `thzdaq mcp`, the bench's tools for agents (Claude Code, Codex) over MCP stdio on the `mcp` SDK: a client of the daemon as `mcp:<agent>`; its tools are those of `thzdaq_api.tools` (operations of `thzdaq_api.catalog`, the set the assistant in the window gets too, answered in short text with units by `thzdaq_api.present`), described as MCP takes them (`tools.py`), run in a thread with their progress (`bench.py`), resources (`resources.py`). The command line finds it by the entry point `thzdaq.cli`, never by import. The guides agents and the assistant read (`AGENTS.md` of a workspace, `thzdaq://guide/<topic>`, the assistant's system prompt) are package data of `thzdaq_api` (`assistant/*.md`, `guides.py`: the rules are written once, in `agents.md`, and the assistant reads them as its section).
- `packages/thzdaq-gui` (`thzdaq_gui`): PySide6 + PySide6-QtAds + pyqtgraph application in the layout of the old app: the window only assembles the parts (`main_window.py`), docks by name and where they open (`docking.py`, names in `dock_names.py`), graph and device docks that follow the graphs and the station (`graph_docks.py`, `device_docks.py`): one layout, base docks (Setup, Data, Log, Processes, Daemon, Editor, Console) pinned to the side bars without a close button or a menu, a device dock never placed opens floating and a closed one where it was, docks (`docks/`: Setup, device docks with raw commands to the instrument in a folded Advanced section (`raw.py`) and scans (`ScanBox`), Data, Log: the program's records and what each measurement tells, filtered by measurement, Processes: what runs now, `processes.py`), graph docks (`graphs.py`; runs started by other clients reach them through `run_graphs.py`), dock search (`navigator.py`: the Devices and Graphs menus as a searchable tree by type, Ctrl+K from anywhere in the program; `Places`: docks, measurements and consoles, each shown by its owner, and `reveal` of any name agents point at), what agents ask of the window (`guide.py`, `WindowGuide`: the one owner of `ui_*` for this window, asking `Places`, the run bar, the forms and the docks; names of what they point at, a field `measure:<procedure>/<field>` and a control `run:start`, in `dock_names.py`; `overlay.py`, `OverlayGuide`: the highlight with its text over the window, following its anchor, gone on a click, Escape or typing there), the bar on top (`runbar.py`: the list of measurements by group with New measurement… and From an example…, running ones with a turning icon; ⚙ drops down the chosen one's form (`popup.py`); graphs, comment, Start, Check, Stop, progress), the forms of measurements, no docks: one per procedure, built when asked for, following the catalog (`measure_forms.py`; `docks/measure.py`: devices and parameters, the run; `docks/custom.py`: Code, where each declared plot goes, the script's output to the Log), run controls as a view of a run's status (`run_controls.py`), file dialogs that remember their folder (`folders.py`), the window's workspace and its File menu (`workspace.py`, `workspace_menu.py`), its settings (`workspace_settings.py`: the Python of its scripts, found and checked by the session's `models/interpreter.py` apart from the window), VS Code for a folder, a script or a line of it (`external_editor.py`), the assistant (dock Assistant, pinned right): without Qt in `assistant/` (`provider.py`: an OpenAI-compatible `chat/completions` client and the providers' Test, `keys.py`: keys in `keyring`, `prompt.py`: the system prompt, `conversation.py`: the loop with the tools of `thzdaq_api.tools`, a step limit, Stop, `hints.py`: what the model is asked about code where the person types and what of its answer is taken), its view model `models/assistant.py` (model servers in the settings; a turn in a thread of its own, told back by queued signals; the session's `assistant_lab()` calls the daemon as `assistant`, an agent), the chat `docks/assistant.py` (a tool call is a folded card) and the servers' dialog `docks/providers.py`; Python consoles as tabs of the Console dock (`console_docks.py`; a console's tab `docks/console.py`: the output above (`console_output.py`: blocks, ANSI colours, places of a traceback as links to Editor), the input on the script editor (`ConsoleInput`: Enter runs a complete block, history, Ctrl+R, Ctrl+C); its model `models/console.py`; its kernel `kernel.py`: one thread with an asyncio loop runs jupyter_client's async manager and client, what the kernel tells reaches Qt as signals; the session deletes kernels, never they themselves), scripts' files as tabs of the Editor dock (`code_docks.py`; plain tabs closed with a question about unsaved changes, by a middle click too, moved by dragging: `docks/tabbed.py`, `TabbedDock`, the container of a bottom dock of tabs; a file's tab `docks/code.py`: the editor `editor.py` with line numbers, pygments, jedi and the bench's completions, Save, Check, Run, Ask, In console (Run selection Alt+Shift+E, Run file), pieces to insert, changes from disk, the script a measurement kept from Data; its model `models/code.py`); a change looked at hunk by hunk in the editor, ✓/✗ for each and for all (`review.py` without Qt: a change made outside, proposed or compared; `review_bar.py`): changes of a file on disk and what the assistant proposes; the assistant's hints in the editor and the console's input (`models/hints.py`, `HintsModel`: the one owner of these calls to the model, each a `Request` of whoever asked): the grey ghost after a pause (Tab takes it), Ctrl+I for code asked in words (`ask_box.py`), Fix of a failed run or block, all of them proposals, what a script printed (`script_output.py`), dark theme with orange accents and qtawesome icons (`theme.py`). The GUI is a client of the daemon: the session works with a `Lab` (`connect_or_start()` in the app, a `LocalLab` in tests), view models in `models/` (run, device, daemon, scripts the daemon runs, a script's file, a console; `runs.py` routes each run's events to one run model, the runs of other clients too) call it, the Daemon dock (`docks/daemon.py`) shows and controls the daemon. With `--plot <id|file>` the program is only the plots window of one measurement (`viewer.py`: its snapshot, then its events, or a file).
- `stations/`: bench profiles (YAML, version 2: instruments with `devices`; ids name the kind of device, e.g. `power_supply_3`). `main.py` is the GUI entry point, and with `--serve` the daemon a built program's clients start; `cli_main.py` is the entry point of the built `thzdaq-cli`. `assets/` holds the pixel app icon (`thzdaq.ico`, `thzdaq.icns`, drawn by `assets/make_icon.py`; rerun it after changing the drawing). `firmware/` keeps device firmware (Arduino grid rotators).

Dependencies point one way: clients (gui, cli, mcp) → api ← core → instruments and core → analysis; the daemon → core and api. `uv run lint-imports` checks the boundaries (contracts in the root `pyproject.toml`).

## Architecture Rules — Required

Fix the design, not the symptom. A change that only works with a hack is not done: restructure, or stop and ask.

- **One-way dependencies, no cycles.** Between packages gui → core → instruments; inside the GUI the entry point (`app.py`) → the windows (`main_window.py`, it only assembles; the plots window `viewer.py`) → their parts (`docking.py`, `graph_docks.py`, `device_docks.py`, `code_docks.py`, `runbar.py`, `measure_forms.py`, `run_graphs.py`) → docks (`docks/`) → widgets and view models (`forms.py`, `run_controls.py`, `collapsible.py`, `popup.py`) → `theme.py`, `settings.py`, `dock_names.py`. A lower module never imports a higher one; it tells through Qt signals or callbacks it is given.
- **One owner per responsibility.** New behaviour goes into the object that owns the concept, not into `MainWindow` or into a widget that happens to be near. A concept lives in one place (dock names in `dock_names.py`, dialog folders in `folders.py`, a run's state in `RunStatus`); never parse or rebuild it elsewhere.
- **Polymorphism over branching.** What differs by kind or device is an object asked for its answer (capability interfaces, `Run` for the controls), not `if kind == …` / `isinstance` chains spread over callers.
- **State in models, widgets are views.** Widgets show a model and call its methods; they never read another widget's labels, buttons or progress bars to learn state.
- **No hacks.** No flags that silence a path for one caller, no sleeps or timers to "let it settle", no retries, no `getattr(self, "_x", default)` for attributes that may not exist, no catch-all `except` to hide a failure, no dead code left behind. If a third-party library (Qt, ADS, pyqtgraph) needs a workaround, it lives in the module that wraps that library (ADS: `docking.py`), runs once at the point where the library's behaviour causes the problem, and its comment names that behaviour.
- **Prove it.** A bug fix reproduces the bug first (a test, or a script on simulators) and checks the fix against it.

### Target boundaries (daemon work, `docs/daemon.md` → «Пакеты, слои и границы»)

New code follows these boundaries now; existing code moves there during milestone M1.

- **Packages.** `thzdaq-api` (contract and client: operations, DTO, events, errors, the measurement file format, `RemoteLab`, `connect_or_start`; depends only on `msgspec`) ← `thzdaq-core` (domain and use cases) → `thzdaq-instruments` and `thzdaq-analysis` (pure calculations, numpy only, imports no ThzDAQ package); `thzdaq-daemon` (process, HTTP + SSE, the server-side composition root) → core and api. Clients `thzdaq-gui`, `thzdaq-cli`, `thzdaq-mcp` import only `thzdaq_api`, never `thzdaq_core`, `thzdaq_instruments`, `thzdaq_analysis` (analysis is a daemon operation; scripts and notebooks may import it) or `thzdaq_daemon`. `thzdaq` is the PyPI meta-package with extras. Only the root `main.py` knows both the GUI and the daemon.
- **Layers in core.** `domain/` (station, `GuardedPort`, procedures, parameters, plots, measurement, leases) ← `application/` (handlers, dispatcher, policy, approvals, runner, events, lanes, polling, scripts, workspaces, ports, `LocalLab`) ← `adapters/` (JSON store, YAML profiles, journal). The domain touches no files or clocks and starts no threads; it gets them through ports and the run context.
- **Use cases.** One operation = one Struct of arguments in its area module of `thzdaq_api` (`devices.py`, `measurements.py`, `station.py`, ...), listed in `catalog.py`, and one stateless handler class in `thzdaq_core/application/handlers/<area>.py`, registered by the explicit list in `application/assembly.py`. Every call from outside goes through the dispatcher: arguments → handler → events (policy comes with rights, milestone M2). A manual write checks the leases just before writing. Procedures inside the daemon talk to their devices directly, not through the dispatcher.
- **Contract types.** DTO, operation arguments and events are `msgspec` Structs in `thzdaq-api`; JSON schemas are generated from them, never written by hand. Values with units travel as strings and are parsed once, by the daemon.
- **GUI.** View models in `thzdaq_gui/models/` are QObjects on QtCore that call `Lab`; they never import QtWidgets. Widgets show a view model and call its methods. One bridge turns `RemoteLab` events into Qt signals. Forms come from `ProcedureInfo` schemas, graphs from `PlotInfo`, analysis from daemon operations.
- **Vocabulary.** Quantity keys and units live in instruments, a procedure's name, slots and plots on its class, shared procedure parameters and axis labels in `domain/measurements/procedures/common.py`, operation names, event types and error codes in api, GUI settings keys in one GUI module. Use them by import; `tests/test_architecture.py` fails on a function body, a phrase shown to people or a dotted/slashed identifier written in two modules (a phrase that only looks the same goes into its `ALLOWED` with the reason).
- **Enforcement.** import-linter contracts in the root `pyproject.toml` run in pre-commit and CI next to the duplicate test; a broken boundary fails the build.

## Build, Test, and Development Commands

- `uv sync` creates or updates `.venv`; `uv lock` after changing any `pyproject.toml`.
- `uv run python main.py --station stations/2sb.example.yaml --simulate` runs the GUI on simulators.
- `uv run thzdaq [--simulate] run <procedure> [--device slot=device] [--set name=value]` runs a measurement in the daemon and follows it (parameters typed as `describe` shows them, a sweep `start:stop:points`); `uv run thzdaq procedures` / `describe <procedure>` show what exists; the daemon loads a profile with `thzdaq daemon start --station <profile>` or `thzdaq station load <profile>`.
- `uv run thzdaq [--simulate] script start <file.py> [--allow set:<device>|raw:<instrument>] [-- args]` runs a script in the daemon apart from the terminal (`script list|logs <id> [-f]|stop <id>`); `python <file.py>` with `from thzdaq import connect` runs it in the terminal. A script has the rights of whoever started it: a person's changes the bench as the person would in a dock (what a dock confirms is asked), an agent's (`CLAUDECODE`, `CODEX_SANDBOX…`, `THZDAQ_AGENT` in its environment; `script:agent:<name>`) asks as the agent does, and an agent's `--allow` allows nothing.
- `uv run thzdaq [--simulate] raw <instrument> "<command>" [--answer] [--share]` sends an instrument a command its driver does not wrap (`lab.raw` in Python, Advanced in its dock): a query (with `?`) answers; a write, which no limit checks, is confirmed by a person (`--yes`), needs `--allow raw:<instrument>` or a person's yes in a person's script (within a measurement the yes holds until it ends), and is refused to agents and their scripts; the devices on the instrument are read again after it. An instrument without a driver: `instrument("gauge_1", driver="generic.scpi", connection="tcp://…", x=reading(...), y=setting(...))` at the top of a script puts it into the profile once a person allows it (Setup → Add instrument → Generic (raw) does it by hand).
- `uv run thzdaq [--simulate] plot <id|file> [--table T --x X --y Y [--group G]]` opens the plots of a measurement in a window of their own (`lab.plot`, `run.show()`, `m.show()` in Python), apart from the terminal.
- `uv run thzdaq init [<folder>] [--station <name>] [--agents]` makes a workspace (`thzdaq.toml`, `data/`, `scripts/`); commands run in it or below it measure there, and `uv run thzdaq gui` opens the window in it.
- `uv run thzdaq init [<folder>] --python <env folder or interpreter>` / `uv run thzdaq python show|set <path>|set --own|list` choose the Python of a workspace's scripts (written into its `thzdaq.toml`, relative when inside it): the bench's own measurements started there, `script start` (unless `--python`), the window's Run and its consoles' new kernels run with it; checked to have `thzdaq` of the program's version (`uv pip install --python <python> thzdaq==<version>` mends it). Without one, the program's own Python, as a build's is.
- `uv run thzdaq [--simulate] agent-setup <folder>` lets Claude Code and Codex measure in a folder: `.mcp.json`, `.codex/config.toml` (trusted projects) and `AGENTS.md` for them; they start `thzdaq mcp` by its absolute path.
- `uv run thzdaq-station check <profile> --simulate` checks a bench profile as a file, without the daemon.
- `uv run python check_console.py [dist/ThzDAQ/thzdaq-cli]` starts a console's kernel as the window does, without a display (runs, interrupts, restarts, stops it): from sources, or with a build's `thzdaq-cli` (the release's smoke test).
- `uv run python check_scripts.py [dist/ThzDAQ/thzdaq-cli]` imports what scripts import (every example's imports, ours, the standard library as `script_modules.py` names it for `ThzDAQ.spec`) with this Python or a build's `thzdaq-cli run-script` (the release's smoke test).
- `uv run thzdaq-daemon --station <profile> [--simulate] [--idle-timeout 0]` runs the bench daemon in the terminal; clients start it themselves through `thzdaq_api.host.connect_or_start()` (its log: `thzdaq[-sim]-daemon.log` in the temp folder).
- `uv run pytest` runs all package tests (GUI tests run offscreen); `uv run pytest packages/thzdaq-core` for one package.
- `sh build.sh` / `build.bat [name]` build the PyInstaller distribution into `dist/` from `ThzDAQ.spec`: `ThzDAQ` (windowed: the GUI, `--serve` the daemon) and `thzdaq-cli` (console) over one `_internal`; the release smoke test starts, asks and stops the build's daemon with `thzdaq-cli`.
- `uvx pre-commit run --all-files` runs Black, autoflake, hygiene hooks and `lint-imports` before committing; `uv run lint-imports` checks the architecture boundaries alone.
- `uv run python release.py X.Y.Z` (or `X.Y.Z-beta.N`: a pre-release on GitHub and PyPI, a new number for every beta) stamps one version on the program (`thzdaq_gui/version.py`, as the tag spells it) and on every package in `packages/` (PEP 440, `X.Y.ZbN`; the packages require each other at exactly it), runs `uv lock`, tags `vX.Y.Z` and pushes (`--again` moves an existing tag to the current commit after fixes and builds it again; PyPI keeps the packages it got first). `.github/workflows/release.yml` then tests, builds the Windows x64 zip and publishes the GitHub release that Help → Check for updates installs (`thzdaq_gui/updates.py`, standalone `thzdaq_gui/updater.py` built as `updater.exe`); its `packages` job builds and checks the packages, its `pypi` job publishes them with the account's API token (repository secret `PYPI_API_TOKEN`). `.github/workflows/ci.yml` runs the tests on every push.
- PyPI packages: `thzdaq` (the client: `thzdaq-api` and `thzdaq-cli`, no numpy or drivers; extras `analysis`, `daemon`, `mcp`, `gui`, `all`) and every `thzdaq-*`, MIT (`LICENSE` copied into each package). `uv build --all-packages -o dist/packages` builds them; `uv run --package thzdaq-api python check_packages.py dist/packages` installs them as a user gets them into clean environments; `tests/test_packages.py` checks one version, exact pins and the same metadata everywhere. A new package in `packages/` gets the same metadata, a `LICENSE` copy; the account token publishes it, a new project included.

## RTK (Rust Token Killer) — Required

RTK is installed and available on `PATH`. Agents must use RTK for every supported shell command by default to reduce command-output token usage. Do not run the raw equivalent unless exact unfiltered output is required, RTK does not support the command, or RTK fails. If RTK fails, fall back to the underlying command so work can continue.

Required command mappings include:

- `git status`, `git diff`, and `git log` → `rtk git status`, `rtk git diff`, and `rtk git log`.
- `git add`, `git commit`, `git push`, and `git pull` → the matching `rtk git ...` command.
- `rg` searches → `rtk rg <pattern> <path>`. Use `rtk grep` only when a `grep` binary is available on `PATH`.
- Large file reads → `rtk read <file>`.
- Directory listings and file searches → `rtk ls <path>` and `rtk find <pattern> <path>`.
- Python test runs → `rtk test uv run pytest ...`.

Run `rtk --version` to verify the installation and `rtk gain` to inspect token savings.

## Python and uv — Required

All Python environment and command interactions must go through `uv`: use `uv sync`, `uv add`/`uv remove` (with `--package <member>` for workspace packages), and `uv run ...`. Do not invoke `pip` directly or manually maintain a separate virtual environment. Keep every `pyproject.toml` and `uv.lock` committed and synchronized.

## Coding Style & Naming Conventions

Python with 4-space indentation, formatted by Black; autoflake removes unused imports. Values are SI inside the code (Hz, V, A, K, s, Pa), power in dBm, angles in degrees; display units live only in parameters and plots. New instruments implement capability interfaces (`thzdaq_instruments.capabilities`), declare their passport (`limits`) and get a simulator plus contract tests; a setpoint names the methods that set it (`Quantity.setters`) so the guard sees every call; new measurements are `Procedure` subclasses with a `guide` (how to measure with it, for agents and the assistant) added to `BUILTIN` in `thzdaq_core/domain/measurements/procedures/__init__.py`, named `<group>.<what is measured>_vs_<what is changed>` in `thzdaq_api/procedures.py` (a renamed one leaves its old name in `RENAMED` there, which files, commands and saved forms still use); a parameter has a `group` (`Group` in `procedures/common.py`) and, when it is used only with another's value, a line in the procedure's `shown_if`; every run's file keeps the plots it is drawn with. Keep comments short and reserve them for non-obvious hardware, timing, or UI behavior.

## Testing Guidelines

Tests live next to each package (`packages/*/tests`, `test_*.py`, pytest); `tests/` at the root checks the whole repository (architecture rules). Drivers are tested against protocol emulators on `FakeLink` and the shared capability contracts in `packages/thzdaq-instruments/tests/contracts.py`; procedures run on simulators; GUI tests run offscreen. Hardware is never needed for tests. For changes that need real instruments, document the bench and steps used.

During work run the tests of what you touched (its package, or its test files); run the full suite only before a merge, and say in the report which you ran. Tests stay fast: sweeps of a few points, zero settles and delays in their parameters, waits on a condition (asking a run's state with `WaitMeasurement(timeout=0)`), never on a fixed time.

## Commit & Pull Request Guidelines

Short imperative messages, optionally with a conventional prefix (`feat:`, `fix:`, `docs:`). Pull requests describe the affected package, list manual test steps (bench, profile, simulate or hardware), mention profile changes in `stations/`, and include screenshots for visible UI changes.

No AI attribution anywhere in the history: commit messages, tags, pull requests and release notes carry no `Co-Authored-By` trailer for an AI assistant, no "Generated with …" line and no other mention of the assistant or model. The author of every commit is the repository owner. This rule overrides any default attribution an agent or tool would add.

## Security & Configuration Tips

Do not commit credentials or machine-specific settings. Keep generated outputs (`dist/`, `build/`, `data/`, logs) out of review unless they are intentional reference artifacts.
