# Workplan: быстрая ВАХ (ветка `fast_iv`)

Только I-V. Сейчас `sis.current_vs_voltage` на каждую точку шлёт `BIAS:DEVn:VOLT`, ждёт и читает
`VOLT?`/`CURR?` по SCPI — около 0,1 с на точку и больше, 351 точка — минута. Модуль смещения блока
Scontel умеет развёртку сам: ему дают начало, конец, шаг и время на точку, и он присылает точки
потоком. По SCPI этого нет — только бинарными кадрами по тому же сокету (порт 9876).

Каждый этап — отдельный коммит, тесты — только того, что тронуто; полный набор — перед merge.

## Протокол (ControlUnit4_Software)

Источник — `/Users/yarvod/Labs/scripts/ControlUnit4_Software`: команды `Libs/StarProtocol/star_prc_commands.h`
(`BS_SetSweepParams` 0x30, `BS_StartSweep` 0x31, `BS_StopSweep` 0x32, `BS_SweepData` 0x33,
`BS_SetMode` 0x18, `BS_SetVoltage` 0x14), структуры `star_prc_structs.h`, сервер
`System/TcpIpServer` (`CommandParsers/serverrawdatacommandparser.cpp`, `devicerawdatacommandparser.cpp`),
клиент `Libs/CuPlugins/Interfaces/cutcpsocketiointerface.cpp`, как запускает развёртку SisMeasurer —
`User/SisMeasurer/mainwindow.cpp:317`.

- Кадр: `[адрес][команда][длина][данные]`, little-endian. Адрес модуля = N из `BIAS:DEVn`, сервер —
  `0xFF`. Ответ — кадр того же вида.
- Сервер считает **один `readAll()` с сокета одной командой**: кадры шлются по одному, следующий —
  после ответа на предыдущий. Текстовые SCPI и кадры различает по третьему байту (длина).
  Ответа модуля ждёт 100 мс.
- Последовательность SisMeasurer:

| Шаг | Кадр |
|---|---|
| параметры | `[N][0x30][20]` + `<fffIB3x`: start, stop, step (В), `timeStep_ms`, mode (1 — по напряжению) |
| режим U | `[N][0x18][1][0x01]` |
| начальное напряжение | `[N][0x14][4]` + float, пауза ~0,5 с |
| pipe mode | `[0xFF][0x04][0]` → ответ `[0xFF][0x04][0]` |
| старт | `[N][0x31][0]` |
| точки | `[N][0x33][12]`: ток f32 (A), напряжение f32 (В), время u32; кадр длиной 4 — конец |
| стоп | `[N][0x32][0]` (SisMeasurer повторяет до 10 раз) |
| выход из pipe mode | `[0xFF][0x05][0]` |
| вернуть режим и напряжение | |

- Pipe mode: сервер пересылает клиенту кадры развёртки и принимает команды только от него.
- Смещения (offsets) драйвера в бинарном пути не применяются: начало и конец — минус смещение
  напряжения, точки — плюс смещения.

# Workplan: Keysight U2002H (ветка `keisight_power_sensor`)

Новый прибор: USB-датчик средней мощности Keysight (Agilent) U2002H, 50 MHz – 24 GHz,
−50…+30 dBm, вход до +33 dBm (2 W). Свой драйвер со своими методами, тип устройства
`power_meter`, возможность `PowerDetector`: процедуры (Y-фактор, 2SB, монитор) берут его как NRX.

Каждый этап — отдельный коммит, тесты — только того, что тронуто; полный набор — перед merge.

## Этап 0. Модель устройства: всё объявлено, ничего не угадывается

Правило: каждое сопоставление (прибор ↔ возможность, возможность ↔ величины и действия, слот ↔
устройство, драйвер ↔ симулятор, профиль ↔ настройки) объявляет один раз его владелец, а
проверяет тест или сама конструкция. Во время работы ничего не выводится из имён.

Сейчас `capabilities_of(cls)` — `issubclass(cls, <Protocol>)`, то есть совпадение имён методов.
Тип прибора (`device_type`) их не заменит: это один ярлык на прибор, а процедурам нужно
поведение, и оно с типом не совпадает — канал Rigol умеет `OutputProtection`, каналы HMP2030 и
Keithley нет; `PowerLevel` есть у генератора и у ZVA; в слот `detector: PowerDetector` годятся
NRX и U2002H; у каналов и sub-device свои возможности. Тип остаётся ярлыком (id, иконки,
группы). Плохо не то, что возможности не от типа, а то, что их никто не объявляет:

- случайное совпадение имени делает прибор чужой возможностью: проверено, класс с
  `get_frequency`/`set_frequency` — `FrequencySource`, попадает в слоты генераторов, получает
  уставку `frequency` и проверку её пределов;
- опечатка или недописанный метод молча убирает возможность — прибор пропадает из слотов без
  ошибки; сигнатуры и единицы не проверяются вовсе;
- порты (`GuardedPort`, `AttributePort`) отдают методы прибора через `__getattr__`, и
  `quantities.declared()` узнаёт возможности порта через `isinstance`. С Python 3.12
  `isinstance` для Protocol смотрит атрибуты статически и делегирование не видит: проверено, у
  `SimPowerMeter` за `PortAdapter` на 3.12 пропадает величина `power`. Программа закреплена на
  `<3.12`, но `thzdaq-core` и `thzdaq-daemon` на PyPI разрешают `>=3.11`, так что демон из
  `thzdaq[daemon]` на 3.12 теряет величины возможностей у приборов за портами. Пределы уставок не
  задеты: они строятся по классу (`Station.quantities`), не по порту.

Где сейчас угадывается и как должно быть:

| Сопоставление | Сейчас | Должно быть |
|---|---|---|
| прибор ↔ возможности | совпадение имён методов (`runtime_checkable Protocol`) | наследование ABC |
| возможность ↔ величины, действия | таблицы `CAPABILITY_QUANTITIES`, `CAPABILITY_ACTIONS` отдельно от возможностей | атрибуты самой возможности: `PowerDetector.quantities = (POWER,)`, `LoadSwitch.actions = (TO_HOT, TO_COLD)` |
| порт ↔ возможности части | `__getattr__` отдаёт любой метод драйвера; `isinstance` по порту (на 3.12+ слеп) | порт — класс, реализующий те же ABC; его методы построены по объявлению, сеттеры возможности охраняются, потому что возможность их объявила; чего нет в объявлении, того у порта нет |
| процедура ↔ необязательное умение | `hasattr(port, "set_voltage_precise")`, `hasattr(spectrum, "set_continuous_sweep")`, `getattr(spectrum, "trigger", None)`, `getattr(load, f"to_{state}")` | объявленная возможность (`PreciseVoltageSource` у SIS bias) или метод возможности, который реализует каждый её прибор (однократная развёртка у `SpectrumAnalyzer`), `LoadSwitch.to(load)` |
| профиль ↔ настройки прибора | два пути: `options` конструктора (NRX `averaging`, `aperture_time` пишутся при открытии) и `persistent` величины (их пишут только симулятору) | один путь — `persistent` величины; прибор объявляет, кто хранит его настройки (сам — генератор с OEM-головой; программа — NRX, U2002H), станция пишет их при открытии тем, кто не хранит |
| драйвер ↔ симулятор | два дерева классов парой в `DRIVERS`, расходятся (у симуляторов YIG, чоппера, сетки есть `RawCommands`; `SimPowerMeter` с настройками NRX — симулятор любого измерителя) | тест: у симулятора те же возможности, величины, действия; позже — симуляция ниже драйвера |
| тип прибора ↔ возможности | не связаны | тип — ярлык (id, иконка); тест: `power_meter` всегда `PowerDetector` |

Слои — кто чем владеет (направления import-linter уже держит):

- `thzdaq_instruments`: транспорт → драйвер (протокол прибора); возможности — контракт: методы,
  их величины (единицы, сеттеры), действия; описание части (`quantities_of`, `actions_of`) —
  только из объявлений; симуляторы.
- `thzdaq_core.domain.station`: устройство — порт, реализующий объявленные возможности части;
  охрана — по объявлению; настройки из профиля — по объявлению прибора, кто их хранит.
- `thzdaq_core.domain.measurements`: слоты по возможностям, процедура зовёт только их. Новый
  контракт import-linter: процедуры не импортируют `thzdaq_instruments.drivers`, `.sim`,
  `.transport` (сейчас и так не импортируют — закрепить).
- api и клиенты: величины и действия по ключу — так уже.

Чего не делать: таблицу «тип → возможности»; большой базовый класс на тип (`PowerMeter` со всем
подряд — апертура NRX, частота поправки U2002H: подкласс либо врёт, либо бросает «не умею»,
это нарушает подстановку Лисков); `hasattr` в процедурах; два пути настроек; прокси через
`__getattr__`.

Порядок — коммитами. 0.1–0.3 нужны до U2002H; 0.4–0.5 трогают ядро и процедуры, их можно
отдельной веткой.

### 0.4 Порт реализует возможности

- [x] Класс порта для набора возможностей строится один раз (кэш) из их ABC: каждый метод
  делегирует части, сеттеры, объявленные возможностью, идут через охрану. `isinstance(port,
  PowerDetector)` — правда по объявлению, `__getattr__` уходит, `declared()` спрашивает порт.
  Сделано: `port_class(класс части)` — `GuardedPort` с возможностями части (самыми
  уточнёнными базами) и её объявленными `quantities`/`actions`; `part_of` ушёл. Тесты:
  недекларированный метод драйвера порту недоступен, каждый сеттер каждой возможности идёт
  через охрану, метод возможности не может занять имя порта.
- [x] Своё у части (NRX `averaging`, действие `zero` у U2002H) — только по ключу величины или
  действия, через ту же охрану, как это уже делают api и клиенты. Порт: `read(quantities)`,
  `write(quantity, value)` (уставка — через охрану: частота поправки U2002H тоже),
  `act(action, arguments)`; так зовут api и мониторинг.
- [x] `AttributePort` (атрибуты SIS перед каждым вызовом) — тот же класс порта с шагом перед
  вызовом (`Attributes`, его даёт вид устройства).
- [x] Порт отдаёт только объявленное, поэтому здесь же объявлено то, что процедуры брали у
  драйверов мимо возможностей: `PreciseVoltageSource(VoltageSource)` у канала SIS bias и его

### Потом (в backlog)

Симуляция ниже драйвера: симулятор — тот же драйвер над эмулятором прибора (эмуляторы для
`FakeLink` уже есть в тестах) и модель стенда, которую эмуляторы делят (горячая нагрузка,
фильтр ПЧ, дрейф). Тогда симулятор не может разойтись с драйвером по построению, а тесты на
симуляторах гоняют настоящий код драйверов. Большая работа: модель стенда, эмуляторы не-SCPI
приборов (Modbus, HTTP).

Как это у pymeasure (0.16.0, исходники и документация разработчика):

- Слоя возможностей нет вовсе. Драйвер — класс прибора (`Instrument` + `SCPIMixin`), процедура
  создаёт конкретный драйвер сама (`self.meter = Keithley2000("GPIB::25")` в `startup`);
  заменить прибор — править процедуру. Им это сходит, потому что нет слотов процедур, доков из
  величин и защиты уставок — того, ради чего возможности есть у нас.
- Единообразие — соглашением об именах в документации («у источников питания `current`,
  `voltage`, `voltage_setpoint`, `current_limit`», «выход — `output_enabled`»). Никто это не
  проверяет: та же утиная типизация, что у нас, только без `issubclass`.
- Общий слой типов приборов обсуждают с 2021 года (issue #416, веха 1.0, открыт; #825 —
  сбор типов, пуст). В обсуждении склонялись к составлению из мелких «черт» множественным
  наследованием (как traits у yaq), а не к большим базовым классам `PowerSupply`; тормоз —
  разнобой возможностей внутри типа и принцип Лисков. Это и есть наш этап 0: мелкие возможности,
  объявленные наследованием.
- Что стоит взять:
  - семейство моделей — базовый класс и подклассы, где меняется только диапазон
    (`frequency_values = [0, 3e9]` у их `dynamic=True` свойств). У нас то же даёт `limits`
    (ClassVar): `KeysightU2000` со всеми командами и `KeysightU2002H` с паспортом 50 MHz…24 GHz;
    другие модели U2000 — подклассы в три строки;
  - `SCPIMixin.check_errors()` (читать `SYST:ERR?` до нуля) и `check_set_errors` у свойств —
    проверка после записи. У нас — `errors()` в `ScpiInstrument` для всех SCPI-драйверов;
    U2002H (без дисплея: ошибка видна только в очереди) зовёт его после нуля и настроек.
- Что не брать: процедуры, привязанные к конкретному драйверу, и соглашения об именах вместо
  объявленных интерфейсов. Их тесты протокола (`expected_protocol`: точная последовательность
  запрос — ответ) у нас покрывают эмуляторы на `FakeLink` и `link.written`.

После этапа 0 имена методов драйвера свободны: у U2002H частоту поправки можно звать
`set_frequency`, как в мануале, — генератором он от этого не станет. Таблица этапа 1 ниже
сделана с этими именами: `set_frequency`, `read_temperature`.

## Прибор по мануалу (U2000 Series Programming Guide)

- Интерфейс — USBTMC/USB488, адрес не настраивается. Ресурс VISA вида
  `USB0::<VID>::<PID>::MY54260001::0::INSTR` (VID 0x0957 Agilent или 0x2A8D Keysight, PID модели —
  смотреть `list_resources()` или Keysight Connection Expert; можно дать алиас, тогда ресурс —
  алиас). Нужен VISA-бэкенд: на Windows — Keysight IO Libraries Suite (или NI-VISA).
- Дисплея нет: всё состояние — только то, что задала программа; после переподключения USB
  настройки сброшены к `*RST`.
- `*RST`: `INIT:CONT OFF`, `TRIG:SOUR IMM`, `TRIG:DEL:AUTO ON`, `UNIT:POW DBM`,
  `SENS:FREQ 50 MHz`, `SENS:AVER:STAT ON`, `SENS:AVER:COUN:AUTO ON` (`COUN 4`),
  `SENS:MRAT NORM`, `SENS:CORR:GAIN2:STAT OFF`, автодиапазон, авто-ноль включён.
- `READ?` — новое измерение, ждёт полного фильтра (`TRIG:DEL:AUTO ON`): значение установившееся.
  Только при `INIT:CONT OFF` (иначе −213 «INIT ignored») и `TRIG:SOUR` не `BUS`/`HOLD`.
  Время ≈ длина фильтра / скорость: NORM 20, DOUB 40, FAST до 110 изм./с. Авто-усреднение у
  нижней границы — до 128–256 отсчётов, то есть **6–13 с на одно чтение** в NORM.
- Частота (`SENS:FREQ`) включает поправку АЧХ датчика: без неё всё меряется с поправкой 50 MHz.
- Ноль: внутренний (`CAL:ZERO:TYPE INT`, сигнал можно не снимать) или внешний (`EXT`, вход без
  сигнала; рекомендован ниже −30 dBm), запуск `CAL:ZERO:AUTO ONCE`; ошибка — −231 в
  `SYST:ERR?`. Авто-ноль сам срабатывает при изменении температуры на 5 °C и раз в 24 ч.
- `SENS:TEMP?` — температура датчика, °C.

## Этап 1. Драйвер `KeysightU2002H`

Файл `drivers/keysight.py`: `KeysightU2000(ScpiInstrument, PowerDetector)` — все команды
семейства; `KeysightU2002H(KeysightU2000)` — `driver_key = "keysight.u2002h"`, паспорт
50 MHz…24 GHz, в `DRIVERS`: «Keysight U2002H USB power sensor». `device_type = "power_meter"`.
Возможности: `PowerDetector`, `Identifiable`, `RawCommands` — и только они.

| Метод | SCPI | Заметка |
|---|---|---|
| `connection(resource, timeout=20.0)` | — | `ConnectionSpec(VISA, …)`; таймаут на длинный фильтр и ноль |
| `__init__(transport, *, name)` | — | ничего не пишет; настройки — из профиля при открытии (0.2), прибор их не хранит |
| `test()` | `*IDN?` | модель `U2002H` в ответе |
| `reset()` | `*RST` | |
| `read_power()` | `UNIT:POW DBM;:INIT:CONT OFF;:READ?` | одно сообщение: всегда dBm и одиночное измерение, что бы ни задали сырыми командами; состояния в драйвере нет |
| `set/get_frequency` | `SENS:FREQ` | Hz, частота поправки; генератором датчик не становится (0.1) |
| `set/get_averaging` | `SENS:AVER:STAT` | |
| `set/get_averaging_auto` | `SENS:AVER:COUN:AUTO` | |
| `set/get_averaging_count` | `SENS:AVER:COUN` | 1…1024; сам прибор выключает авто |
| `set/get_measurement_rate` | `SENS:MRAT` | `NORM`/`DOUB`/`FAST` |
| `set/get_offset` | `SENS:CORR:GAIN2`, `:STAT` | dB, −100…+100 (аттенюатор, кабель); 0 при выключенном |
| `read_temperature()` | `SENS:TEMP?` | K (°C + 273.15), величина `sensor_temperature`; термометром не становится |
| `zero()` | `CAL:ZERO:TYPE INT`, `CAL:ZERO:AUTO ONCE`, `*OPC?` | внутренний ноль, ошибка → `InstrumentError` |
| `zero_external()` | то же с `EXT` | |
| `errors()` | `SYST:ERR?` до `+0` | в `ScpiInstrument`, общий для SCPI-драйверов (как `check_errors` у pymeasure) |

Величины — `U2000_QUANTITIES` в `quantities.py` рядом с NRX-овскими (словарь величин живёт там):

- `frequency` «Frequency (correction)», Hz — уставка (`setters=("set_frequency",)`), паспорт
  `limits` 50 MHz…24 GHz: её можно сканировать вместе с частотой ПЧ;
- `averaging`, `averaging_auto`, `averaging_count` (int), `measurement_rate` (choices),
  `offset`, dB — конфигурация, `persistent=True`: профиль хранит, станция пишет их при каждом
  открытии (после переподключения USB датчик сброшен к `*RST`);
- `sensor_temperature`, K — только чтение.

Действия — в `actions.py`, атрибут `actions` драйвера: `zero` «Zero» (внутренний, безопасно) и
`zero_external` «Zero (external)» с `danger`: снять сигнал со входа, иначе он станет нулём. Два
действия вместо аргумента — у каждого своё предупреждение.

Тесты (`packages/thzdaq-instruments/tests`):

- [x] `U2000Emulator` в `emulators.py`: `*IDN?` → `Agilent Technologies,U2002H,MY54260001,A1.04.01`,
  составное сообщение чтения, частота, усреднение (счётчик выключает авто), скорость, смещение,
  температура, ноль, `*OPC?`, `SYST:ERR?`; неизвестное — в `errors`.
- [x] `contracts.py`: фабрика `u2002h` в `PowerDetector` (и где перечислены `Identifiable`,
  `RawCommands`).
- [x] `test_keysight.py`: чтение в dBm и одиночное, даже если до этого прибору
  задали `W` и `INIT:CONT ON`; конструктор ничего не пишет, настройки профиля приходят при открытии;
  `capabilities_of(KeysightU2002H)` — ровно три (защита от `FrequencySource`/`Thermometer`);
  ключи конфигурации; ноль шлёт нужную последовательность, −231 → исключение; реестр:
  `find(PowerDetector)` содержит `keysight.u2002h`.
