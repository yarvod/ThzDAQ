# Workplan: smart_agent (issue #3)

Ветка `smart_agent`. Источник: https://github.com/yarvod/ThzDAQ/issues/3, плюс два пожелания сверх
issue: ассистент сам читает данные измерений и анализирует их без скриптов; общий промт агента
редактируется в настройках ассистента.

Порядок: сначала то, на чём стоит всё остальное (производительность и потоки чата, общий интерфейс
сессии), потом возможности. Каждый этап — отдельный коммит (или несколько), тесты — только того,
что тронуто; полный набор — перед merge.

## Что есть сейчас

- Чат: `docks/assistant.py` (виджет на элемент, колонка в `QScrollArea`), `chat_widgets.py`
  (`MessageView` = `QTextBrowser` на сообщение), модель `models/assistant.py` (ход в своём потоке,
  события в GUI очередями сигналов), `assistant/conversation.py` (цикл с инструментами),
  `assistant/provider.py` (`chat/completions`, стрим SSE).
- Окно серверов `docks/providers.py` уже есть: список слева, форма справа, Test и Save.
- Инструменты стенда — `thzdaq_api/tools.py`, общие для ассистента и `thzdaq mcp`.
- Промт — `assistant/prompt.py`: `assistant.md` + правила из `agents.md` + стенд сейчас +
  процедуры. Человек его не меняет.
- Данные измерений модели не видны: `summarize_measurement` даёт только число записей, диапазоны
  колонок и скалярные результаты. `GetRunSnapshot` (строки) и `AnalyzeIv` есть в API, но среди
  инструментов их нет. Чтобы посмотреть точки, ассистенту приходится писать скрипт.

## Почему чат подвисает (измерено)

Замер offscreen на текущем коде (скрипт в scratchpad, `Bubble.show_item` на каждый кусок стрима
по 4 символа):

| ответ, символов | кусков | GUI занят |
|---|---|---|
| 1 000 | 250 | 0.22 с |
| 4 000 | 1 000 | 3.1 с |
| 12 000 | 3 000 | 34 с |

Рост квадратичный: на каждый кусок `MessageView.show_text` делает `setMarkdown` всего текста,
обходит все фрагменты документа (`_code_blocks`) и пересчитывает высоту. Модель пишет быстрее,
чем GUI успевает перерисовать, очередь сигналов растёт, и окно стоит. Длина чата сама по себе
стрим почти не замедляет (2 000 символов в конце чата из 0/50/200 ответов: 0.95/0.81/0.90 с),
но длинный диалог — это длинные ответы, мысли и ответы инструментов. Ещё:

- мысль (`ThoughtCard`) так же перерисовывается целиком на каждый кусок и раз в секунду в `tick`;
- карточка вызова перерисовывает весь ответ инструмента на каждое событие прогресса;
- 4 ресайза дока при 200 ответах — 0.54 с (около 135 мс на ресайз): все документы
  перекладываются, и свёрнутые карточки тоже;
- GUI может ждать поток хода: `_another_lab` и `close` берут `_reach_lock`, пока поток под ним
  подключается к демону.

## Этап 0. Производительность и потоки чата

- [x] Тесты, которые воспроизводят проблему без замеров времени: куски, пришедшие пока окно
  занято, меняют элемент один раз; выделение в уже показанном тексте переживает стрим; тело
  свёрнутой карточки не строится; смена лаборатории не ждёт подключения хода. Все четыре падали
  на старом коде.
- [x] Куски стрима сливаются без таймеров: поток хода кладёт события в одну очередь и будит GUI,
  только когда она была пуста; GUI забирает её целиком, `item_changed` — раз на элемент за заход.
- [x] `MessageView` дописывает, а не перерисовывает: законченные блоки Markdown (после пустой
  строки вне ```-блока, не перед элементом списка) вставляются один раз, хвост — заново;
  простой текст — только новыми буквами. Раскладка документа — только при смене ширины (она и
  была главной ценой: `setTextWidth` на каждый рост высоты).
- [x] Карточки мысли и вызова строят тело при первом раскрытии; `tick` трогает только идущую
  мысль (`AssistantModel.thinking()`).
- [x] GUI не ждёт поток хода: `_reach_lock` только меняет поля, подключение и закрытие — вне его.
- [x] Повторный замер: стрим линейный.

| ответ, символов | было | стало |
|---|---|---|
| 4 000 | 3.1 с | 0.30 с |
| 12 000 | 34 с | 0.93 с |
| 30 000 | — | 2.5 с (≈0.33 мс на кусок) |

  Ресайз чата из 200 ответов: около 70 мс на ресайз (было 135). Длинный список или код-блок
  остаётся в хвосте, пока не закончится, и стоит дороже на кусок, пока стримится.

Тесты: `test_assistant.py`, `test_assistant_dock.py`, новые тесты `MessageView`.

## Этап 1. Ассистент читает данные измерений сам

- [ ] Операция `ReadMeasurement` в `thzdaq_api/measurements.py`: измерение по id (бегущее или
  законченное, из его файла), таблица, нужные колонки, диапазон по колонке, не больше N строк
  (по умолчанию 200, потолок около 2 000) с равномерным прореживанием; значения в SI, единицы в
  заголовке. Обработчик в `thzdaq_core/application/handlers/measurements.py`, в `assembly.py` и
  `catalog.py`.
- [ ] Инструмент `read_measurement` в `thzdaq_api/tools.py` с компактным ответом
  (`present.table`: CSV-подобные строки, заголовок с единицами, сколько строк пропущено). Он же
  появится у Claude Code и Codex через `thzdaq mcp`.
- [ ] `analyze_iv` как инструмент по id измерения и колонкам напряжения и тока (модель не гоняет
  массивы через контекст): анализ считает демон.
- [ ] Гайды: правило 8 в `agents.md` («Read the file to analyse it; never pass arrays through
  tools») и абзац о данных в `assistant.md` («You cannot read its file») переписать: сначала
  `summarize_measurement`, потом `read_measurement` нужных колонок; файл или скрипт — для тяжёлой
  обработки.

Тесты: пакеты api и core (новая операция на симуляторе), `thzdaq-mcp` (список инструментов),
`test_assistant.py` (вызов инструмента).

## Этап 2. Общий промт, редактируемый в настройках

Встроенный промт уже есть, его собирает `assistant/prompt.py` к каждому разговору (около 2 400 слов
текста плюс состояние стенда):

1. `thzdaq_api/assistant/assistant.md` (~280 слов): роль ассистента в окне, вызовы видны
   карточками, изменения ждут согласия человека; отвечать на языке человека и коротко; план перед
   измерением; `ui_*`, чтобы показывать, а не описывать; данные — только через
   `summarize_measurement`; измерения живут в демоне дольше чата.
2. Раздел Rules из `thzdaq_api/assistant/agents.md`: 13 правил, общих с Claude Code и Codex
   (сначала describe, единицы, рабочие диапазоны, опасные шаги, согласие человека, длинные
   измерения, один свип на прибор, данные, вопросы человеку, raw-команды, свои измерения,
   графики, показ в окне).
3. «The bench now»: профиль, приборы с возможностями, соединения — собирается у демона.
4. «Procedures»: по строке на процедуру со слотами.
5. Раздел «A measurement of the bench's own» из `agents.md`: формат своего измерения.

Решено: инструкции человека дополняют встроенный промт, а не заменяют его. Хранятся в настройках
программы и общие для всех рабочих папок.

- [ ] Страница «Instructions» в настройках ассистента: редактор инструкций человека, просмотр
  собранного встроенного промта только для чтения.
- [ ] `prompt.py` собирает: встроенный → правила → инструкции человека → стенд → процедуры.
  Изменение действует со следующего хода (`forget_bench`).
- [ ] Те же инструкции уходят в Codex (у `codex-acp` есть возможность сессии `systemPrompt`).

Тесты: `test_assistant.py` (промт собран с инструкциями), тест страницы настроек.

## Этап 5. Codex через ACP

Проверено по исходникам `@agentclientprotocol/codex-acp` 2.7.0: stdio-агент ACP, сам запускает
Codex App Server (Codex в пакете или `CODEX_PATH`); умеет `session/load`, список, resume, fork,
close; `session/set_config_option` (модель, reasoning effort, режим); изображения в промте;
`usage_update` (заполнение контекста); stdio и HTTP MCP-серверы от клиента; `systemPrompt` от
клиента; события генерации изображений; сообщения посреди хода (`_session/steering`).
Локально стоит Codex CLI 0.144.1 (через nvm); `codex-acp` и настольного Codex нет.

Клиент ACP — официальный Python SDK `agent-client-protocol` 1.0.0 (wheel 128 КБ; зависит от
`pydantic`, который уже есть в `uv.lock` через `mcp` и попадает в сборку). В нём есть всё нужное:
`initialize`, `new/load/list/resume/fork/close/delete_session`, `set_config_option`, `prompt`,
`cancel`, `ext_method` (для steering), на стороне клиента — `session_update`,
`request_permission`, elicitation. SDK асинхронный; asyncio не мешает: консоль уже держит
asyncio-цикл в отдельном потоке (`kernel.py`), здесь так же. `QtAsyncio` в PySide6 пока
technical preview, он не нужен.

- [ ] Клиент ACP в `assistant/acp.py`, единственный модуль, который импортирует SDK: процесс
  адаптера (команда из настроек, по умолчанию `npx -y @agentclientprotocol/codex-acp`), один
  поток с asyncio-циклом (как `kernel.py`), события в Qt сигналами. `initialize`: проверка версии протокола и адаптера,
  понятное сообщение о несовместимой версии; если нужна авторизация — подсказка `codex login`
  (ключи и пароли программа не вводит).
- [ ] `session/new` в рабочей папке, `mcpServers` = `thzdaq mcp` той же командой, что пишет
  `agent-setup` (абсолютный путь, `--workspace`, `--simulate` по окну). Codex ходит к стенду как
  агент `mcp:…`, демон проверяет права и спрашивает человека.
- [ ] `session/prompt` (текст и изображения), `session/update` → общие события (текст, мысли,
  вызовы инструментов и их обновления, план, `usage_update`); Stop = `session/cancel`.
- [ ] `session/request_permission` (команды и правки файлов самого Codex) — карточка в чате с
  вариантами, которые прислал Codex. Режим по умолчанию — `workspace-write` (пишет в рабочей
  папке, остальное спрашивает), меняется в настройках Codex.
- [ ] Модель и reasoning effort — через config options сессии; расход за ответ — из результата
  хода; лимиты аккаунта — отдельной секцией «Расхода», если App Server их присылает.
- [ ] История Codex: `session/list` по рабочей папке и `session/load` (повтор событий → элементы).
- [ ] Настройки Codex: команда адаптера, путь к `codex` (`CODEX_PATH`), режим по умолчанию.
- [ ] Ручная проверка на симуляторе с Codex CLI и с настольным Codex: создать чат, сменить модель,
  открыть из истории, вызвать инструмент стенда; отдельно — какие сессии CLI и приложения видит
  адаптер. Шаги и результат — в описании PR.

Тесты: фейковый ACP-агент (скрипт на stdio) для `acp.py` и модели, без Codex и сети.

## Этап 6. Изображения в ответах

- [ ] Элемент-изображение в ответе (и в ответе без текста): по ширине чата с сохранением
  пропорций (`heightForWidth`); по клику — просмотр с масштабом, копированием и сохранением
  оригинала.
- [ ] Генерация во встроенном режиме: у сервера модели необязательная «модель изображений»

  когда она задана. Ход работы виден, Stop работает, недоступность и ошибка — заметкой в чате.
- [ ] В режиме Codex — изображения из его событий генерации и просмотра.

Тесты: `test_assistant.py` (генерация на фейковом сервере), `test_assistant_dock.py` (показ).

## Решения

1. Промт: инструкции человека дополняют встроенный, хранятся в настройках программы.
2. История встроенного Assistant хранится в данных программы с ключом по рабочей папке.
3. Клиент ACP — официальный SDK `agent-client-protocol` в потоке с asyncio-циклом (если не будет
   возражений; нужен только на этапе 5).
4. Codex по умолчанию в режиме `workspace-write`.
