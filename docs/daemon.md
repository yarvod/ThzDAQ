# ThzDAQ: демон стенда, клиенты GUI/CLI/MCP и ассистент в GUI

## Зачем

Сейчас приборы держит GUI-процесс: `Session` → `Station`. Ручные команды и опрос идут через
`DeviceWorker` (поток на прибор), измерения — через `QtRunner` на док. CLI `thzdaq run`
открывает приборы сам. Если GUI открыт, два процесса делят Prologix/R&S, а lock-файл
(`app.instance_lock`) только предупреждает. Действия из CLI GUI не видит.

Цели:
1. Стенд держит один процесс — **демон** `thzdaq serve`. GUI, CLI, MCP (Claude Code, Codex по
   подписке) и ассистент — его клиенты. Работают одновременно, и любое изменение сразу видно
   всем.
2. Чат-ассистент в GUI. Провайдеры (URL, ключ, модель, параметры) в форме, активный
   выбирается. Ассистент видит устройства и их состояние, предлагает и делает измерения,
   подсвечивает, куда нажать. Интерфейс он видит как структуру (`ui_state`), без скриншотов.
3. Регулируемые права. Агент спрашивает разрешение или задаёт вопрос с вариантами, человек
   подтверждает, отклоняет или отвечает своим текстом.

Решено:
- сразу демон, GUI и CLI всегда клиенты, режима «GUI как хост» нет;
- API только localhost;
- порядок — вехи М1–М4 (раздел «Вехи»): демон без потери функций → права и MCP → скрипты
  и рабочие папки → ассистент и редактор;
- симуляция — отдельный демон, работающий одновременно с реальным;
- в сборке два exe: оконный `ThzDAQ.exe` и консольный `thzdaq-cli.exe`;
- **архитектура** (раздел «Пакеты, слои и границы»):
  - контракт и клиент — отдельный пакет `thzdaq-api`; GUI, CLI, MCP и скрипты зависят только
    от него;
  - демон — пакет `thzdaq-daemon`: процесс, HTTP и SSE, точка сборки серверной стороны;
  - CLI — пакет `thzdaq-cli`, такой же клиент, как GUI и MCP;
  - `thzdaq-core` делится на `domain` / `application` / `adapters`;
  - юзкейсы — обработчик на операцию и один диспетчер с общим конвейером поверх доменных
    сервисов;
  - DTO, аргументы операций и события — `msgspec`, JSON-схемы генерируются;
  - GUI — модели вида на QtCore и виджеты, которые только показывают;
  - анализ (I-V, шумы, 2SB) — операции демона;
  - каждое понятие определено один раз, у своего владельца; тест ловит дубли;
  - границы проверяет import-linter в pre-commit и CI;
  - на PyPI одно имя `thzdaq` с extras.

## Архитектура

```
 Claude Code / Codex
        │ MCP по stdio
        ▼
 thzdaq mcp (thzdaq-mcp) ─┐                         ┌──────── thzdaq-daemon ───────────────┐
                          │   HTTP JSON + SSE       │ HTTP → диспетчер: права → аренды →    │
 thzdaq (thzdaq-cli) ─────┼── 127.0.0.1 + токен ───►│ обработчик → журнал и событие         │
                          │   контракт thzdaq-api   │ thzdaq-core: домен и юзкейсы          │
 GUI (thzdaq-gui) ────────┘   (RemoteLab)           │   → Station → полосы → TransportPool  │
  └ ассистент (в процессе GUI)                      └───────────────────────────────────────┘
      модель по API (Qwen, ...) ⇄ инструменты = те же операции
      через RemoteLab GUI, origin = assistant
```

- **MCP — только для внешних агентов.** MCP нужен, чтобы чужая программа (Claude Code,
  Codex) получила наши инструменты. Ассистент внутри GUI — наш код с обеих сторон: он берёт
  описания инструментов из того же каталога операций (`thzdaq_api.catalog`) и вызывает их
  через `RemoteLab`, который у GUI уже есть. Ходить через `thzdaq mcp` значило бы
  добавить подпроцесс, stdio и asyncio в GUI ради того же результата. Набор инструментов у
  ассистента и у MCP-агентов одинаковый, потому что оба строятся из одного каталога.
  Подключать к ассистенту *чужие* MCP-серверы (поиск по документации и т. п.) можно позже,
  как отдельную возможность.

- **Операции, а не прокси приборов.** Клиент никогда не держит объект прибора. Доступно:
  `devices`, `quantities(ref)`, `read(ref)`, `set(ref,key,value)`, `call(ref,action,args)`,
  `connections`, `reset_connection`, `procedures`, `describe`, `start(procedure, params,
  devices, comment)` → run id, `status`, `cancel`, `abort`, `measurements`, `measurement(id)`,
  `set_comment`, `station.get/update`, `subscribe_poll(ref, interval)`, UI-операции.

  У каждого вызова есть `origin` (gui, cli, mcp:<имя>, assistant). `Procedure.run` выполняется
  в демоне с настоящими драйверами, наружу идут только события.
- **Действия устройств декларативно**, как `Quantity` (`thzdaq_instruments/actions.py`):
  `Action(key, title, call, arguments, danger, changes)`, аргументы с единицами и пределами.
  Они выводятся из возможностей (`LoadSwitch` → `to_hot/to_cold`, `Compressor` →
  `turn_on/off` с предупреждением, `SpectrumAnalyzer/NetworkAnalyzer` → `configure` и
  `read_trace`), драйвер добавляет свои (чоппер: `start_rotation`, `stop`). У поворотного
  устройства действия нет: угол — задаваемая величина. Действия, которым нужен профиль, даёт
  вид устройства: `sis_bias` → `write_calibration` (коэффициенты из метаданных устройства).
  `changes=False` у чтения (трасса): оно не мешает развёртке. Особые группы доков
  (`ChopperGroup`, `CompressorGroup`, `TraceGroup`, `SisBiasGroup`) уже выполняют эти
  действия; в клиенте GUI они станут вызовами `call_action`.
- **Одновременные обращения:**
  1. полоса прибора — очередь и поток на прибор, перенос `_Lane` в `thzdaq_core/application/lanes.py`: ручные операции
     всех клиентов идут по порядку;
  2. блокировка линка (`Link.RLock`): байты на одной шине не перемешиваются;
  3. **аренда**: кто сейчас пользуется устройством и как. Владелец аренды — конкретное
     измерение или сессия скрипта (их id), а не тип клиента: два окна GUI, док прибора и
     измерение из того же GUI — разные участники. Аренда не запрещает, а **требует явного
     намерения только там, где чужое изменение портит данные**. Подробно — ниже, «Аренды и
     параллельные измерения».
  4. **опрос по подписке**: один опрос устройства с наименьшим из интервалов подписчиков,
     значения рассылаются всем.
- **Поток уставок внутри измерения.** Процедура на развёртке делает тысячи set. Событие
  `quantity_set` по ним сливается (доки получают последнее значение не чаще ~10 раз в
  секунду), а журнал «кто, что, было → стало» пишет только ручные, скриптовые и агентские
  изменения. Точки самого измерения и так лежат в его таблицах.
- **UI-операции адресуются окну.** У каждого окна GUI свой id клиента. `ui_*` идут в окно,
  из которого агента позвали (ассистент — в своё окно); у MCP-агента — в последнее
  активное окно или в явно указанное `client`.
- **События** с порядковым номером:
  - `quantity_set`, `values`, `action_done`;
  - `measurement_started/records/progress/log/finished` (записи пачками);
  - `connection_changed`, `station_changed`, `lease_changed`;
  - `approval_requested/answered`, `ui_*`, `log`.

  Новый клиент получает **снимок**: идущие измерения с таблицами, уставки, соединения,
  аренды, номер последнего события. Дальше — поток SSE; после разрыва клиент догоняет с
  номера (кольцевой буфер; если пропущено слишком много, берёт новый снимок).
- **Жизненный цикл** — запуск, подключение, статус и управление описаны в разделе
  «Запуск, подключение и управление демоном».
- **Один писатель:** профиль стенда, данные (`MeasurementStore`), комментарии — только через
  демон. Демон держит по хранилищу на каждую рабочую папку, в которой запускались
  измерения (раздел «Рабочая папка»). QSettings (окно, перспективы, последние значения
  форм) остаются в GUI.
- Профиль — свойство демона; GUI меняет его операцией `station.load`.
- **Симуляция — отдельный демон.** Реальный демон держит приборы, демон-симулятор работает на
  симуляторах. Они живут одновременно: у каждого свои файлы (`thzdaq-host.json` /
  `thzdaq-sim-host.json`, своя блокировка). Клиент с `--simulate` сам идёт в демон-симулятор
  и при необходимости запускает его. Отладка скрипта на симуляторах возможна, пока на стенде
  идёт реальное измерение.
  - Окно GUI подключено к одному демону. В заголовке и индикаторе видно, к какому:
    симулятор выделен цветом и подписью SIMULATED. Переключение — в меню.
  - Данные симулятора пишутся в ту же рабочую папку, но с пометкой `simulated` в
    измерении. Data показывает пометку.
- **Изменение профиля во время измерения.** `station.update` / `station.load`, затрагивающие
  прибор под арендой (новая связь, удаление, другой драйвер), получают отказ с перечнем
  измерений. Изменения, не касающиеся занятых приборов (новое устройство, пределы
  свободного прибора), применяются сразу.
- Транспорт: `ThreadingHTTPServer` из stdlib, JSON-запросы и SSE. Потоки, без asyncio и
  новых зависимостей. Слушает только 127.0.0.1, токен в заголовке.
- **Зачем токен на localhost.** 127.0.0.1 закрыт от сети, но не от этого компьютера:
  - любая веб-страница, открытая в браузере на ПК стенда, может отправить запрос на
    `http://127.0.0.1:<порт>`. Простой POST уходит без проверки CORS, а через DNS rebinding
    страница может даже читать ответы. Без токена чужой сайт мог бы выставить смещение;
  - другие пользователи и программы на том же ПК (общий лабораторный компьютер, удалённый
    рабочий стол);
  - случайное подключение к чужому или устаревшему демону (вторая установка, тесты): токен из
    файла хоста однозначно указывает на нужный процесс.

  Пользователю это ничего не стоит: клиенты читают токен из `thzdaq-host.json` сами. Файл
  лежит во временной папке пользователя, доступной только ему. Дополнительно сервер
  отклоняет запросы с чужим `Host` (защита от DNS rebinding) и с `Origin` браузера.

### Аренды и параллельные измерения
Параллельные измерения на общих устройствах — нормальная работа стенда. Монитор часами
пишет T, P и I, пока идут другие измерения. Во время P-V подкручивают мощность LO. Скрипт
переключает выход блока питания (переключатель ПЧ), которым пользуется идущее 2SB-измерение.
Всё это должно работать, как работает сейчас. Ошибкой почти всегда бывает только одно: два
участника одновременно задают величину, по которой кто-то из них делает развёртку.

**Как слот использует устройство** — объявляет процедура для каждого слота (`slot_modes`):
- `read` — только читает (детектор, термометр; все слоты `monitor.time`);
- `shared` — задаёт, но чужие изменения ему не мешают: LO, переключатель ПЧ, нагрузка,
  сетка между точками. **Это режим по умолчанию**;
- `exclusive` — по этому устройству идёт развёртка, и чужие изменения портят данные:
  `bias` в I-V и P-V, `sis1` / `sis2` в 2SB-картах, `coil` в I-CL.

**Правила:**
- Внутри своего измерения или скрипта всё разрешено без вопросов (кроме пределов `safety` и
  опасных действий, которые всегда требуют подтверждения).
- `read` и `shared` ни с чем не конфликтуют. Действие выполняется сразу. В журнал и в
  `metadata.interactions` *обоих* измерений пишется, кто, что, было → стало, когда:
  «#43 (script:ifswitch) set power_supply_1:1 output false во время #42».
- **Конфликт — только на `exclusive`:** задать устройство, по которому сейчас идёт чужая
  развёртка, или запустить второе измерение, которому оно нужно как `exclusive` или `shared`.
  Нужно явное намерение:
  - человек (GUI, интерактивный CLI) — один вопрос «sis_bias_1 развёртывается измерением #42
    (I-V), всё равно?»; при запуске измерения — один вопрос на всё измерение, а не на
    каждую точку;
  - скрипт — заранее: `lab.measurement(..., share=["sis_bias_1"])` или
    `thzdaq script start --share sis_bias_1`. Без этого — вопрос человеку (как `ask`);
  - агент — вопрос человеку, а не отказ;
  - ответ «да» записывается в метаданные обоих измерений как `conflict` с тем, кто
    разрешил. В Data у обоих измерений появляется жёлтая пометка.
- Два `exclusive` на одном устройстве одновременно (две развёртки одного смещения) — то же
  явное намерение, но вопрос звучит как предупреждение: «данные обоих измерений будут
  испорчены».
- Встроенные процедуры получают `slot_modes` по смыслу. Если процедура ничего не объявила —
  все её слоты `shared`, то есть ведут себя как сейчас.

### Поток событий (SSE)
- **Измерение.**
  1. `ctx.record()` в потоке демона передаёт запись наблюдателю раннера.
  2. Шина копит записи 50–100 мс и выпускает одним событием `measurement.records`
     `{run, table, rows}` с номером `seq` в кольцевой буфер.
  3. У каждого клиента свой поток HTTP-сервера. Он ждёт новых событий на условной
     переменной и пишет в открытый ответ `id: <seq>`, `event: <тип>`, `data: <json>`.
  4. Поток-читатель `RemoteLab` разбирает события, а мост GUI (`bridge.py`) отдаёт их
     Qt-сигналом моделям вида в GUI-потоке. Графики дописывают точки, а перерисовка идёт по таймеру (20–30 раз в
     секунду), а не на каждую точку.
- **Монитор.** `subscribe_poll(ref, interval)` → планировщик ставит чтение в полосу прибора
  с наименьшим интервалом подписчиков. Если прошлое чтение ещё не закончилось, новое не
  ставится (очередь не растёт). Результат уходит событием `values` всем подписчикам.
- **Демон не ждёт клиентов.** У клиента — только позиция в буфере (`EventBus.wait`).
  Отставший дальше буфера получает `resync` и берёт новый снимок. Медленный клиент не
  тормозит измерение.
- **Переподключение.** Клиент передаёт `Last-Event-ID` — это наш `seq`, — и демон досылает
  пропущенное из буфера, а потом шлёт `heartbeat`: подписка догнала. Если ~2 с событий нет,
  идёт комментарий `: ping` и `heartbeat` (без номера, в буфер не попадает: кто слушает,
  сколько измерений, проблемы). Поток, молчащий дольше 6 с, клиент считает оборванным.
- **Уставки измерения** (`quantity_set` с origin `#<id>`): порты прогона сообщают, что
  задали, а прогон публикует не чаще раза в 0,1 с на величину (отложенное — с ближайшим
  прогрессом или записью, последнее — в конце). Развёртка на тысячи точек — несколько
  событий в секунду, снимок знает последнюю уставку.
- **Большие данные** (трассы VNA и спектроанализатора): массивы как base64 от float64. Если
  трасса больше порога, вместо неё идёт событие-ссылка, а данные забираются запросом
  `GET /measurements/<id>/tables/<table>?since=<n>`.
- **Скорость.** Узкое место — приборы (GPIB через Prologix — 10–30 мс на запрос, NRX — до
  200 мс, SIS-блок — ≥ 50 мс), то есть сотни событий в секунду в худшем случае. SSE по
  localhost даёт задержку около миллисекунды и пропускную способность в мегабайты в секунду.
  Перерисовка в GUI нагружена не больше, чем сейчас, когда `QtRunner` шлёт сигнал на каждую
  запись.
- **Почему SSE, а не WebSocket.** Частые сообщения идут только от сервера к клиенту, а
  команды редкие и идут обычными POST. SSE работает на stdlib, переподключение с
  `Last-Event-ID` совпадает с нашим `seq`, а в браузере есть `EventSource`. WebSocket нужен
  для частых сообщений от клиента или двоичных кадров; ни того ни другого пока нет. Шина
  (`thzdaq_core/application/events.py`) от транспорта не зависит: если понадобится,
  WebSocket станет вторым адаптером в `thzdaq-daemon`, без изменений в core.
- **Бенчмарк в тестах:** 10 тыс. событий через SSE в клиент без потерь и по порядку
  (на ноутбуке разработки — за 0,13 с) и `resync` у клиента, отставшего дальше буфера.

## Пакеты, слои и границы

Правило одно: зависимости направлены внутрь, к домену. Клиенты (GUI, CLI, MCP, скрипты) знают
только контракт. Демон собирает домен и юзкейсы и выставляет их по HTTP. Нарушение границы
ломает сборку: правила проверяет import-linter в pre-commit и CI («Проверка границ»).

### Пакеты
```
thzdaq-gui ──┐
thzdaq-cli ──┼──► thzdaq-api ◄── thzdaq-core ──► thzdaq-instruments
thzdaq-mcp ──┘          ▲             ▲  │
                        └── thzdaq-daemon └──► thzdaq-analysis ◄── скрипты, ноутбуки

thzdaq (мета, PyPI) ──► thzdaq-cli + thzdaq-api; extras [analysis] [daemon] [mcp] [gui] [all]
```
Стрелка — «импортирует». `core → api`: юзкейсы реализуют операции контракта и возвращают его
DTO, поэтому типы на границе одни на всех и прослойка «доменный объект → DTO» не нужна.

- **thzdaq-api** — контракт и клиент. Зависит только от `msgspec`; без Qt, numpy и драйверов.
  - Операции — в модулях областей (`devices.py`, `measurements.py`, `station.py`,
    `leases.py`, `analysis.py`, `events.py`), явный список в `catalog.py`. У каждой — Struct
    аргументов с именем, типом результата, классом прав, признаком «долгая» и описанием для
    модели. JSON-схема генерируется из Struct.
  - DTO: `DeviceInfo`, `QuantityInfo`, `ActionInfo`, `ProcedureInfo` (параметры — JSON-схема,
    слоты, графики), `PlotInfo`, `RunInfo`, `MeasurementSummary`, `ConnectionInfo`,
    `LeaseInfo`, `DaemonStatus`.
  - События — объединение с тегом (`QuantitySet`, `Values`, `MeasurementRecords`, …) и снимок
    `Snapshot`.
  - Ошибки — `ErrorCode` и `LabError(code, message, hint)`, одна таблица кодов на всех.
  - Формат файла измерения `thzdaq-measurement` v1: это публичный формат данных, его читают
    скрипты, `thzdaq show` и Data без демона.
  - `Lab` (Protocol: `call(args) → result`, `events()`), `RemoteLab` (HTTP + SSE на stdlib),
    файл хоста, `connect_or_start()`, `api_version`.
  - Клиентские функции и объекты устройств (`lab.read/set/...`, `lab["sis_bias_1"]`).
  - Значения с единицами (`"2.3mV"`) клиент передаёт строкой, разбирает их демон теми же
    единицами, что и драйверы: разбора единиц в двух местах нет.
- **thzdaq-core** — домен и юзкейсы, без сети и Qt.
- **thzdaq-analysis** — чистые расчёты: анализ I-V (Rn, Rj, Q, щель), шумовая температура по
  горячей и холодной нагрузке, дробовой шум, подавление боковой полосы 2SB, перевод дБ. На
  входе массивы и параметры, на выходе dataclass результата; без файлов, станции и единиц
  отображения. Зависит только от numpy. Core вызывает его в процедурах и в операциях анализа
  (`analyze_iv`); GUI и CLI получают анализ этими операциями, чтобы у всех клиентов был один
  результат, а скрипты и ноутбуки могут импортировать его сами (`thzdaq[analysis]`).
- **thzdaq-instruments** — приборы как сейчас: возможности (`capabilities.py`) — порты домена к
  приборам, драйверы и транспорты — адаптеры к железу.
- **thzdaq-daemon** — процесс демона. Точка сборки серверной стороны (станция, хранилища,
  сервисы, обработчики, диспетчер), HTTP и SSE поверх диспетчера, файлы хоста и блокировка,
  `daemon.json`, таймаут простоя, лог. Своей логики операций нет: только транспорт и жизненный
  цикл.
- **thzdaq-cli** — команда `thzdaq`: аргументы → вызовы `Lab` → вывод. `thzdaq daemon start`
  запускает исполняемый файл демона, а не импортирует его.
- **thzdaq-mcp** — `thzdaq mcp`: инструменты из каталога api, вызовы через `RemoteLab`.
- **thzdaq-gui** — окно, клиент `Lab`.
- **thzdaq** — мета-пакет для PyPI («Пакеты на PyPI»). Модуль `thzdaq` реэкспортирует
  `connect` и клиентские функции из api.
- `main.py` в корне — вход сборки: `ThzDAQ.exe` запускает GUI, с `--serve` — демона, с `--plot`
  — окно графиков. Это единственное место вне пакетов, которое знает и про GUI, и про демона.

### Слои внутри core
```
thzdaq_core/
  domain/       станция и профиль, GuardedPort и пределы, процедуры и параметры, графики
                (PlotSpec), измерение, аренды, действия устройств, анализ, SIS
  application/  обработчики операций, диспетчер и конвейер, права и подтверждения, раннер,
                шина событий и снимок, полосы приборов, опрос по подписке, сессии скриптов,
                рабочие папки; порты (Protocol): хранилище измерений, профили, часы, журнал;
                LocalLab
  adapters/     JSON-хранилище измерений, YAML-профили, журнал в файл
  cli/          локальные thzdaq и thzdaq-station, пока их не заменит thzdaq-cli
```
- `application → domain`; `adapters → application` (порты) и `domain`. Домен не импортирует ни
  application, ни adapters.
- Время, файлы и потоки — только через порты или в application (полосы, опрос, раннер). Домен
  тестируется без них.

### Юзкейсы: обработчик на операцию
- Одна операция — один класс-обработчик (`application/handlers/<область>.py`):
  - реализует операцию из api: тип аргументов и результата берёт оттуда;
  - зависимости — в конструкторе (доменные и прикладные сервисы);
  - `handle(args, origin) → result`; своего состояния нет, поэтому параллельные вызовы
    безопасны.
- **Диспетчер** `dispatch(args, origin)` — единственный вход для HTTP и `LocalLab`. Конвейер у
  всех операций один:
  1. разбор и проверка аргументов (`msgspec`);
  2. права: `Policy` (origin × класс операции) → `allow` / `ask` / `deny`. Ожидание ответа
     человека идёт вне блокировок, после ответа проверка повторяется;
  3. обработчик;
  4. журнал и событие.

  Аренду ручная запись проверяет прямо перед записью. Аренды меняются только при старте и
  конце измерений, а процедуры работают с устройствами напрямую, не через полосы, поэтому
  проверка внутри задания полосы ничего бы не добавила. Сквозные вещи пишутся один раз;
  новая операция — новый класс, остальные не трогаются.
- **Регистрация** — явным списком в точке сборки демона, а не побочным эффектом импорта: граф
  зависимостей виден в одном месте. Тест: у каждой операции api ровно один обработчик.
- **Измерение внутри демона идёт мимо диспетчера.** Процедура пишет в устройства через
  `GuardedPort`, держа аренды со старта, поэтому тысячи точек развёртки конвейер не проходят.
  Цена диспетчера — микросекунды; прибор отвечает за 10–200 мс.
- **`LocalLab`** — реализация `Lab` поверх диспетчера в том же процессе. Это не режим работы
  GUI («GUI как хост» не делаем), а основа тестов: одни и те же контрактные тесты идут на
  `LocalLab` и на `RemoteLab` с сервером в потоке.

### GUI-клиент
- GUI зависит только от thzdaq-api и Qt: прибора, `Station` и процедур в нём нет.
- **Модели вида** (`thzdaq_gui/models/`) — QObject на QtCore. Они держат состояние дока
  (запуск, величины устройства, список измерений, процессы, демон) и вызывают `Lab`.
  QtWidgets не импортируют и тестируются без окон.
- **Виджеты** только показывают модель и зовут её методы; состояние друг у друга не читают
  (как `RunStatus` и `RunControls` уже сейчас).
- **Мост событий** один: поток-читатель `RemoteLab` → сигнал Qt (queued) → модели вида. Он
  заменяет `DeviceWorker` и `QtRunner`.
- Формы параметров и слотов строятся из `ProcedureInfo` (JSON-схема), графики — из `PlotInfo`.
  GUI не импортирует `Parameter` и `PlotSpec`.
- Анализ (I-V, шумы, 2SB) — операции демона (`analyze_iv(measurement, params)` → DTO). GUI,
  CLI, MCP и ассистент получают один и тот же расчёт, numpy в GUI не нужен.
- Настройки окна (QSettings) — объект из точки сборки GUI, все ключи в одном модуле.

### Словарь без дублей
Каждое понятие определено один раз, в слое, которому оно принадлежит, и используется
импортом:
- ключи величин и единицы — thzdaq-instruments (`quantities.py`, `units.py`); имена
  возможностей — классы `capabilities.py`, в DTO и скриптах — строки с этими именами;
- имя процедуры — атрибут её класса; слоты и графики — объявления процедуры;
- общие параметры процедур (Settle time, Hot load, Load switch delay) и подписи осей —
  фабрики и константы в `domain/measurements/procedures/common.py`;
- имена операций, типы событий, коды ошибок — thzdaq-api;
- ключи настроек GUI — один модуль GUI.

`tests/test_architecture.py` падает, если в двух модулях написано одно и то же тело функции,
одна и та же фраза для людей или один и тот же идентификатор с точкой или слешем (имя
процедуры, ключ настроек, id драйвера). Фраза, которая только совпадает по словам (два
понятия в двух слоях), записывается в его `ALLOWED` с причиной; запись, которая больше не
повторяется, тест тоже не пропустит.

### Проверка границ
import-linter, контракты в корневом `pyproject.toml`, запуск в pre-commit и CI:
- thzdaq-gui, thzdaq-cli и thzdaq-mcp не импортируют thzdaq_core, thzdaq_instruments и
  thzdaq_daemon;
- thzdaq-api не импортирует ничего из ThzDAQ;
- слои core идут в одну сторону: adapters → application → domain;
- thzdaq_core и thzdaq_instruments не импортируют Qt и HTTP-сервер;
- модели вида GUI не импортируют QtWidgets;
- циклов внутри пакетов нет.

## Запуск, подключение и управление демоном

Цель: пользователь не думает о демоне. Запустил GUI или любую команду `thzdaq`, и всё
работает. Но в любой момент из GUI или CLI можно увидеть, жив ли демон, что у него внутри,
и остановить или перезапустить его.

### Файлы демона
Все файлы лежат во временной папке системы (`THZDAQ_DAEMON_DIR` — другая папка: тесты,
второй стенд на одной машине); у демона-симулятора те же файлы с префиксом `thzdaq-sim`
вместо `thzdaq` (`thzdaq_api.host.DaemonFiles`):
- `thzdaq-daemon.lock` — эксклюзивная блокировка ОС (`msvcrt.locking` / `fcntl.flock`,
  `thzdaq_api.lock`), которую держит живой демон. Гарантирует один демон на машину.
- `thzdaq-host.json` — пишется атомарно после того, как сервер готов принимать запросы:
  `pid`, `port`, `token`, `api_version`, `app_version`, `executable` (какая установка
  запустила), `started`, `station`, `simulate`. Удаляется при выходе — только своим
  демоном, по `pid`. Рабочие папки передаёт каждый клиент сам, в файле хоста их нет.
- `thzdaq-daemon-start.lock` — короткая блокировка на время автозапуска, чтобы два клиента
  не запустили два демона.
- `thzdaq-daemon.log` — stdout и stderr демона; больше 5 МБ — при следующем запуске
  отодвигается в `.log.1`.

Состояние демона между запусками (последний профиль, таймаут простоя) хранится в
`daemon.json` в папке программы (`--home`; из исходников — рабочая папка), как `stations/`
и `data/`; у симулятора — `daemon-sim.json`: его профиль не профиль стенда. QSettings для
этого не подходят: демон не зависит от Qt.

### Подключение клиента (общая функция `connect_or_start()` в `thzdaq_api.host`)
1. Прочитать `thzdaq-host.json`. Если файл есть, проверить `GET /health` с токеном
   (таймаут ~1 с).
2. Ответ получен и `api_version` совпадает → подключиться.
3. Файла нет, процесса с таким `pid` нет или `/health` не отвечает → файл устарел. Под
   блокировкой `thzdaq-daemon-start.lock` ещё раз проверить: вдруг другой клиент уже
   запустил демон. Если нет — удалить устаревший файл и запустить демон.
4. Запуск отвязан от клиента, чтобы демон пережил его закрытие:
   - Windows: `CREATE_NEW_PROCESS_GROUP | DETACHED_PROCESS | CREATE_NO_WINDOW`;
   - POSIX: `start_new_session=True`;
   - stdout и stderr идут в лог демона.

   Команда: из исходников и из окружения с `thzdaq[daemon]` — `python -m thzdaq_daemon`
   (`thzdaq-daemon`), из сборки — `ThzDAQ.exe --serve` (тот же exe, без окна; шаг 8). Сборка при каждом запуске записывает
   свой путь в файл установки пользователя; по нему её находит клиент, поставленный с PyPI
   без демона.

   Параметры: `--station` — профиль, который передал клиент (GUI — свой последний из
   QSettings, CLI — из `--station`), иначе последний из `daemon.json`; `--simulate`, если
   клиент его просил.
5. Ждать появления `thzdaq-host.json` и ответа `/health` до ~15 с, в GUI с заставкой
   «Запуск демона…». Не дождались — показать хвост лога демона и ошибку (порт, профиль,
   исключение при старте).
6. После подключения: снимок → поток событий. Клиент называет себя в заголовках потока
   (`X-Thzdaq-Client` — gui/cli/mcp/assistant, `X-Thzdaq-Pid`, `X-Thzdaq-Origin`): так
   демон знает, кто слушает, без отдельной операции `hello`.

`RemoteLab` обещает: когда `call()` вернулся, каждая подписка уже услышала события, которые
вызвала операция (ответ называет номер последнего события, `X-Thzdaq-Seq`). Поэтому
контрактные тесты одни и те же на `LocalLab` и `RemoteLab`. Перезапущенный демон слушает
другой порт: клиент находит его по файлу хоста, а подписчики получают `Resync` (новый
демон нумерует события заново).

Флаги и переменные:
- `--no-autostart` / `THZDAQ_NO_AUTOSTART=1` — не запускать, а сообщить «демон не запущен»
  (для скриптов и тестов);
- `THZDAQ_DAEMON_DIR` — другая папка файлов демона (тесты, второй стенд на одной машине).

### Несовпадение версий и установок
- `api_version` не совпадает (GUI из новой сборки, демон от старой или из исходников):
  - измерений нет → предложить перезапуск демона своей версией (GUI — диалог, CLI —
    `--restart-daemon` или вопрос в терминале);
  - измерения идут → работать нельзя: показать, кто запущен и какие измерения идут.
- Отличается только `app_version` → предупреждение в статусе, работа продолжается.
- Профиль демона отличается от того, что просит клиент → клиент не перезапускает демон
  молча. GUI показывает, что загружено, и предлагает переключить (`station.load`); если
  затронуты занятые приборы, переключение запрещено. CLI пишет предупреждение, `--station X`
  с другим профилем без идущих измерений переключает. `simulate` здесь не участвует: это
  другой демон.

### Когда демон завершается
- Живёт, пока есть подключённые клиенты (открытые SSE-потоки) или идут измерения (в том
  числе сессии скриптов).
- **Остановка из GUI.** В диалоге выхода к нынешним пунктам (раскладка, дамп) добавляется
  выбор:
  - «оставить демон работать» — по умолчанию, если идут измерения: они продолжаются;
  - «завершить измерения и остановить демон» — отмена с `on_exit`, затем остановка.

  Если измерений нет, второй пункт отмечен по умолчанию. Если к демону подключены ещё
  клиенты (другое окно GUI, CLI, MCP-агент, скрипт), диалог показывает их, и по умолчанию
  демон остаётся работать. Кроме того, демон останавливается и перезапускается в любой
  момент из GUI (док Daemon) и из CLI.
- Окно GUI ушло, а измерений и других клиентов нет → дальше действует таймаут простоя, как
  без GUI.
- **Без GUI** (демон запустили CLI, скрипт или агент, GUI не открыт): завершается по
  таймауту простоя — по умолчанию 10 мин после ухода последнего клиента и конца измерений;
  настраивается, `0` — никогда. Разовые команды CLI (`read`, `set`) таймер не продлевают
  сверх таймаута.
- **Автозапуск снова.** Демон, завершившийся по таймауту, запустится сам при следующей
  команде, скрипте, агенте или GUI (`connect_or_start()`). Пользователь видит только чуть
  более долгий первый вызов.
- Второй экземпляр GUI теперь не проблема: это просто второй клиент. Предупреждение
  `instance_lock` убирается.

### Живой демон не держит приборы
- Пул закрывает неиспользуемые соединения после 5 с простоя (`pool.close_idle`, как сейчас
  в приложении); следующая команда переподключается сама. Соединение живёт, пока идёт
  измерение, сессия скрипта или есть подписка мониторинга. R&S по сокету выходит из remote,
  когда соединение закрыто.
- **GPIB за Prologix.** Прибор остаётся в REMOTE с заблокированной панелью, пока ему не
  пришлют go-to-local, даже если сокет к Prologix закрыт. Перед закрытием простаивающего
  соединения Prologix пул шлёт `++loc` каждому адресу, к которому обращался. Проверить на
  стенде (E8247C, FSEK30): панель разблокируется, следующая команда снова переводит прибор в
  remote.
- Serial не закрывается: открытие порта перезагружает Arduino.
- В статусе демона видно, какие соединения открыты и почему (измерение, подписка, простой
  N с).

### Статус: что видно о демоне
`GET /status` (и операция `get_daemon_status`; сделано всё, кроме памяти, числа потоков и
последних ошибок лога):
- процесс: pid, версия, установка, время работы, память, число потоков, порт;
- стенд: профиль, `simulate`, открытые приборы;
- клиенты: вид, pid, с какого времени, последняя активность;
- измерения: id, процедура, origin, прогресс, сколько идёт, арендованные устройства;
- полосы приборов: длина очереди, текущее задание и сколько оно висит. Задание дольше 5 с
  помечается как зависшее, как сейчас в `check_device_worker`;
- соединения пула: адрес, статус, какие приборы на нём (`Station.connections()`);
- подписки опроса: устройство, интервал, подписчики;
- события: последний номер, размер буфера;
- последние ошибки и предупреждения лога.

Демон каждые ~2 с шлёт событие `heartbeat` с краткой сводкой. По нему клиент понимает, что
связь жива, и обновляет индикатор без отдельных запросов.

### Управление
Операции демона (класс прав `daemon`, по умолчанию `ask` для mcp/assistant); сделаны
`stop_daemon` и `restart_daemon`, остальные — с CLI-клиентом (шаг 7):
- `daemon.stop(mode)`:
  - `graceful` — отказ, если идут измерения;
  - `cancel` — отменить измерения, выполнить их `on_exit`, выйти;
  - `abort` — ещё и прервать зависшие чтения (`Station.abort`).
- `daemon.restart(mode)` — то же плюс запуск нового процесса с теми же параметрами. Клиенты
  переподключаются сами и получают новый снимок.
- `daemon.kill` — только из CLI и GUI, не по API. Если демон не отвечает, клиент убивает
  процесс по `pid` из файла хоста (`TerminateProcess` / `SIGKILL`). Файлы измерений,
  оставшиеся в `running`, уже читаются как `interrupted`.
- `daemon.reset_lane(instrument)` — сбросить зависшую полосу: прервать ввод-вывод прибора и
  пересоздать поток. Python-поток убить нельзя: зависший поток помечается брошенным и
  уходит, когда чтение прервётся.
- `connections.reset(key)` — как сейчас Reset в Setup → Connections.
- `daemon.logs(tail, follow)` — лог через API.
- `daemon.settings` — таймаут простоя, уровень лога; хранятся в `daemon.json`.

### В GUI
- Индикатор демона в строке состояния:
  - зелёный — OK;
  - жёлтый — есть зависшие полосы или ошибки соединений;
  - красный — нет связи;
  - серый — переподключение.

  В подсказке — версия, время работы, число клиентов и измерений.
- Док **Daemon** (меню Base) — всё из `/status` таблицами и обновляется по `heartbeat`.
  Кнопки:
  - Restart / Stop (с выбором режима, если идут измерения);
  - Kill (если не отвечает);
  - Reset у полос и соединений;
  - Open log (файл и хвост в доке);
  - настройки таймаута.
- Потеря связи: баннер «Нет связи с демоном», управляющие кнопки отключаются, графики и
  данные остаются. Переподключение с нарастающей паузой (0.5 → 5 с). Если процесс умер —
  кнопка «Запустить демон» и, по настройке, автоматический перезапуск. После
  переподключения — новый снимок, доки и графики догоняют состояние.
- Help → About показывает файл хоста, лог демона и `daemon.json`.

### В CLI
- `thzdaq daemon status [--json]` — сводка `/status`. Код выхода: 0 — OK, 1 — есть
  проблемы, 3 — демон не запущен.
- `thzdaq daemon start [--station X] [--simulate] [--foreground]` — `--foreground`
  запускает демон в терминале с логом в консоль (отладка).
- `thzdaq daemon stop|restart [--cancel|--abort] [--force]`.
- `thzdaq daemon kill`.
- `thzdaq daemon logs [-n 100] [-f]`.
- `thzdaq daemon clients`.
- `thzdaq daemon reset-lane INSTRUMENT`, `thzdaq connections [reset KEY]`.
- `thzdaq serve` — синоним `daemon start --foreground` (так его запускает автозапуск).
- Остальные команды (`run`, `set`, ...) подключаются через `connect_or_start()`; одна строка
  в stderr «демон запущен (pid …)», когда его пришлось запустить.

### Обновления и сборка
- Апдейтер перед заменой файлов вызывает `daemon.stop(graceful)`. Идут измерения → обновление
  откладывается с сообщением, как сейчас при отменённом выходе. Демон не ответил → `kill`
  после подтверждения.
- После обновления первый клиент запускает демон уже новой версии (совпадёт
  `executable`/`api_version`).
- Сборка: в папке программы два exe над одними библиотеками (`_internal`). PyInstaller
  собирает их одним spec: два `EXE` в одном `COLLECT`, второй exe добавляет несколько МБ.
  - `ThzDAQ.exe` — оконный (без консоли): GUI, `--serve` (демон без окна; лог в файл),
    `--plot <id>` (окно графиков).
  - `thzdaq-cli.exe` — консольный: всё, что работает через stdio и терминал. Команды как у
    `thzdaq` из PyPI: `thzdaq-cli daemon status`, `run`, `set`, `mcp`, `run-script` (скрипт
    на встроенном Python, вывод виден в терминале и в логе).
  - Почему не один exe: в Windows exe либо консольный, либо оконный. Оконный не даёт
    stdout/stdin (MCP по stdio и вывод CLI не работают), а консольный при запуске GUI
    открывает чёрное окно. Так же устроены `python.exe` / `pythonw.exe`.
  - Почему не `thzdaq.exe`: имена файлов в Windows не различают регистр, и `thzdaq.exe`
    столкнётся с `ThzDAQ.exe` в одной папке.
- **CLI из сборки и CLI из PyPI не конфликтуют.**
  - Из сборки команда — `thzdaq-cli`, из PyPI — `thzdaq`, это разные имена.
  - Оба — клиенты одного демона; несовместимую версию ловит проверка `api_version`.
  - Демон всегда один, кто бы его ни запустил: его держит блокировка.
  - Если на ПК есть и то и другое, `thzdaq daemon status` показывает, какая установка
    держит демон (`executable`).
- Сборка ставится из zip, без установщика, поэтому `thzdaq-cli.exe` не в PATH.
  `thzdaq-cli agent-setup` пишет в `.mcp.json` абсолютный путь к себе, так что PATH агентам
  не нужен. Для терминала — пункт Help → «Add CLI to PATH» (PATH пользователя, с
  подтверждением).
- Апдейтер: Windows не даёт заменить запущенный exe, а `thzdaq-cli.exe mcp` может держать
  открытым Claude Code или Codex. Перед заменой апдейтер находит процессы этой установки
  (`ThzDAQ.exe`, `thzdaq-cli.exe`), показывает их и просит закрыть агентов или завершает
  их с подтверждением. Пока они живы, обновление откладывается.
- Smoke-тест релиза: `ThzDAQ.exe --serve` → `thzdaq-cli.exe daemon status` (код 0) →
  `thzdaq-cli.exe daemon stop`.

## Защита приборов и образцов

### С чего начинали
- У `Quantity` были `minimum/maximum`, но запись их не проверяла. У уставок — смещение SIS,
  ток катушки, выходы блоков питания, мощность и частота генератора — пределов не было.
- Развёртки (`SweepParameter`) диапазон не ограничивали.
- Процедуры вызывают методы драйвера напрямую (`bias.set_voltage(v)`), минуя величины.
  Поэтому проверка только в интерфейсе или API ничего не защищает: защита стоит там, где
  вызывается прибор, — в устройстве, которое выдаёт станция (`GuardedPort`, ниже).
- Что на стенде реально можно повредить (со слов владельца стенда):
  - **переход SIS**: напряжение и ток смещения, скачки, ток катушки, закоротка;
  - **умножитель и LO**: мощность и частота генератора на входе умножительной цепочки,
    включение RF;
  - **компрессор Sumitomo**: и включение, и выключение (выключение — отогрев криостата);
  - **нагреватели LakeShore**: диапазон, уставка, режим выхода.

  Отдельно — запись калибровки в EEPROM SIS-блока. Питание LNA и YIG в обязательный список
  не входит: пределы для него задаются по желанию.

  С агентами добавляется ещё ошибка в единицах: мВ вместо В — это ×1000.
- **Опасные действия** (флаг `danger` у действия или величины): `Compressor.turn_on/off`,
  диапазон, уставка и режим нагревателя LakeShore, `write_calibration`, `set_short`
  (величина `active` SIS-выхода). У нагревателя LakeShore величин пока нет: флаг появится
  вместе с ними.
  Правила для них:
  - для агентов и скриптов всегда `ask`, «разрешить всегда» для них недоступно;
  - карточка подтверждения показывает предупреждение (что произойдёт) и требует ввести
    подтверждение (например, имя устройства), а не просто нажать «Да»;
  - в GUI человек тоже получает диалог с предупреждением перед действием.

### Уровни защиты
1. **Паспортные пределы драйвера** (`thzdaq_instruments.limits`). Это то, что прибор вообще
   принимает. Драйвер объявляет их по ключам величин: `limits` — для самого прибора или
   каждого его канала, `channel_limits` — для каналов, которые отличаются. Сейчас заданы
   номиналы DP832A (CH1/CH2 30 В / 3 А, CH3 5 В / 3 А), HMP2030 (32 В / 5 А), Keithley
   2200-30-5 (30 В / 5 А) и мощность E8247C (до 25 dBm). Частоту E8247C паспорт не
   ограничивает: она показывается с множителем прибора. Диапазон DEV SIS-блока добавим,
   когда его подтвердят на стенде. Паспорт берётся у настоящего драйвера и на симуляторе.
   Значение вне паспорта → `LimitError` до отправки команды: многие приборы молча обрезают
   значение или ставят что-то своё.
2. **Пределы стенда в профиле** — строже паспортных, защищают образец. Раздел `safety`
   профиля (`domain/station/safety.py`), ключ — ссылка на устройство (каналы тоже:
   `power_supply_1:2`), значения в СИ. Числа ниже — только пример формата; настоящие
   пределы задаются для конкретного стенда и образцов:
   ```yaml
   safety:
     limits:
       sis_bias_1:  {voltage_set: {min: -8.0e-3, max: 8.0e-3, warn_min: -6.0e-3, warn_max: 6.0e-3, step: 0.5e-3, rate: 5.0e-3}}
       sis_coil_1:  {current_set: {min: -0.05, max: 0.05, step: 0.005}}
       power_supply_2:1: {voltage_set: {max: 12}, current_set: {max: 0.5}}   # YIG
       signal_generator_1: {power_level: {max: 10, warn_max: 5}, frequency: {min: 10.0e9, max: 14.0e9}}
     safe_state:
       sis_bias_1: {voltage_set: 0}
       sis_coil_1: {current_set: 0}
       signal_generator_1: {output: false}
     hardware_protection: true   # OVP/OCP блоков питания из limits при подключении
   ```
   - `min/max` — жёсткие пределы: отказ;
   - `warn_min/warn_max` — мягкий диапазон внутри `min..max`: за ним `ask` для всех, кроме
     GUI (политика, М2; пока он только показывается в `describe_device`);
   - `step` — наибольший шаг за одну команду: большее изменение идёт лесенкой из равных
     ступеней;
   - `rate` — наибольшая скорость (единиц/с): после каждой ступени ждём `ступень / rate`;
     без `step` не задаётся.

   Профиль, чей раздел называет несуществующее устройство или величину, которую устройство
   не задаёт числом, не загружается: опечатка не должна оставить устройство без защиты.
3. **Где проверяется — одно место.** `Station.device(ref)` отдаёт устройство в обёртке
   `GuardedPort` (`station/ports.py`, поверх `AttributePort`). Уставка называет методы,
   которые её задают (`Quantity.setters`: `set_voltage`, `set_current`, `set_power`,
   `set_frequency`, `tune`, `rotate_to`; у SIS-смещения ещё `set_voltage_precise`), и
   обёртка перехватывает их вызовы для числовых величин. Она проверяет паспорт и пределы
   стенда (`Guard`) и делает лесенку по `step`/`rate`. Через неё идут процедуры, доки, CLI,
   MCP и ассистент — обойти её можно только кодом, который сам лезет в `.target`. Кто, что,
   было → стало — это события `quantity_set` и записи в измерения (аренды), а не обёртка.

   Чтобы не замедлять развёртки:
   - «было» берётся из уставок, записанных через устройство, без запроса к прибору; если
     уставки ещё нет, а лесенка нужна, она читается один раз. Порты одного устройства делят
     эти уставки;
   - паузы лесенки ждут через переданную функцию: у станции — обычная пауза (её даёт тот,
     кто создаёт станцию), у прогона — своя (`RampPause`): пока измерение идёт, отмена
     прерывает лесенку сразу, а восстановление в `on_exit` доводит её до конца;
   - если шаг развёртки меньше `step`, лесенки нет: обёртка ничего не добавляет к обычной
     развёртке.
4. **Проверка до старта измерения.** Параметр процедуры объявляет, куда он идёт:
   `BiasVoltage` — `applies=("bias", VOLTAGE_SET.key)`, `SisBiasSweep(1, …)` — в `sis1`,
   ток катушки — в `coil`, угол сетки — в `grid`, мощность VNA — в `vna`.
   `Procedure.planned()` собирает крайние значения (`Parameter.bounds`), а `Station.require`
   проверяет их против пределов устройства слота вместе с возможностями. Измерение, которое
   упало бы на середине, не начинается, и файл не создаётся. `dry_run` у
   `start_measurement` (проверка, число точек, оценка времени, без приборов) — тот же
   расчёт, делаем вместе с формами из `ProcedureInfo`.
5. **Аппаратная защита.** Если `hardware_protection` включён, при открытии прибора выходы с
   возможностью `OutputProtection` получают OVP/OCP из максимумов `voltage_set` и
   `current_set`, а при изменении пределов — заново. Прибор держит их сам, даже если
   программа зависла или упала. Сейчас это DP832A (`:OUTP:OVP`, `:OUTP:OCP`) и симулятор;
   у HMP2030 и Keithley 2200 добавим, когда проверим на стенде.
6. **Безопасное состояние.** `safe_state` из профиля:
   - операция `safe_state` (сделана; для агентов — `allow`): значения по порядку профиля,
     каждое через `GuardedPort`, то есть лесенкой; отказ одного устройства (конфликт
     аренды без `share`, предел, сбой) не останавливает остальные, ответ говорит, как
     прошло каждое;
   - кнопка в GUI «Всё в безопасное состояние» — с GUI-клиентом (шаг 6);
   - `thzdaq safe` — с CLI-клиентом (шаг 7);
   - автоматически при `daemon.stop --cancel/--abort` — с демоном (шаг 4).

   `on_exit` процедур остаётся: он восстанавливает исходное значение, `safe_state` —
   безопасное.
7. **Проверка после записи** — по желанию, для каждой величины (`verify: true` в `safety`),
   потому что это лишний запрос на каждую точку. Обёртка сравнивает прочитанное с заданным
   (с допуском) и пишет предупреждение при расхождении: прибор обрезал значение или команда
   не дошла. По умолчанию включена только для ручных, скриптовых и агентских изменений, а
   внутри процедур выключена. У SIS-смещения итеративная подгонка уже есть (`scontel.py`,
   `max_iterations`).

### Ошибки единиц и подтверждения
- API и CLI принимают значение с единицей (`"2.3mV"`); голое число — это СИ. Ответ и
  карточка подтверждения всегда показывают значение в единицах показа и изменение:
  «sis_bias_1 voltage: 2.1 mV → 2300 mV (×1000)».
- Изменение больше заданной доли (по умолчанию ×10 или выше `warn`) → `ask` даже там, где
  set разрешён.
- Нет пределов у опасной величины (смещение и катушка SIS, мощность и частота генератора,
  уставка нагревателя) → для агентов каждый set идёт как `ask`: нет пределов — нет
  самостоятельности.

### Кто меняет пределы
- Раздел `safety` меняется только из GUI (Setup → Safety) и CLI с явным
  `thzdaq station safety ...`. Класс прав `station` для mcp и assistant — `deny`, без
  подтверждений: агент не может поднять себе пределы.
- Изменения пределов пишутся в журнал и в историю профиля (`stations/.history/`).

### Блокировки по условиям (позже)
Правила вида «смещение SIS выше X только если `thermometer_1.temperature < 6 K`» или
«RF генератора включается, только если гетеродинный канал не на hot». Это простые условия
над последними прочитанными величинами в `safety.interlocks`. Делаем после пределов, когда
станет видно, какие правила реально нужны на стенде.

## MCP-сервер

### Библиотека
Официальный Python SDK `mcp` (modelcontextprotocol), закреплённый по минорной версии, —
зависимость только пакета `thzdaq-mcp`. Отдельный `fastmcp` 2.x не берём:
- его плюсы (генерация из OpenAPI, прокси, авторизация) нам не нужны;
- `from_openapi` даже вредна: агенту нужен небольшой продуманный набор инструментов с
  хорошими описаниями, а не каждая HTTP-ручка демона.

Используем низкоуровневый `mcp.server.lowlevel.Server`, а не декораторы `FastMCP`: инструменты
генерируются из каталога операций, а не пишутся функциями с type hints. Python 3.11 подходит.
Версию SDK и поддержку возможностей в клиентах проверить перед началом М2.

### Один источник описаний
Операции определены в thzdaq-api (`ops/`): у каждой Struct аргументов с именем, типом
результата, классом прав, признаком «долгая» и описанием для модели. JSON-схема аргументов
генерируется из Struct (`msgspec.json.schema`), руками не пишется. Из этого списка
(`thzdaq_api.catalog`) строятся:
- инструменты MCP (`list_tools` → схемы, `call_tool` → `RemoteLab`);
- инструменты встроенного ассистента (формат OpenAI tools);
- справка CLI и `thzdaq describe-ops`.

Обработчики в core реализуют эти операции; тест проверяет, что у каждой ровно один
обработчик. Добавили операцию — она сразу появилась везде.

### Набор инструментов
- Стенд:
  - `list_devices`;
  - `describe_device(ref)` — величины с единицами и пределами, действия;
  - `read_device(ref)`;
  - `set_quantity(ref, key, value, unit?)`;
  - `call_action(ref, action, args)`;
  - `connections`.
- Измерения:
  - `list_procedures`, `describe_procedure(name)` — схема из `Parameter.describe()`;
  - `start_measurement(procedure, parameters, devices, comment)` — один общий инструмент,
    а не по инструменту на процедуру;
  - `wait_measurement(id, timeout)`, `cancel_measurement(id)`;
  - `list_measurements`, `measurement_summary(id)` — results, число точек, характерные
    значения, без массивов.
- Диалог: `ask_user(question, options, allow_text)`, `wait_answer(id)`.
- Интерфейс: `ui_state`, `ui_open`, `ui_fill_measurement`, `ui_highlight`.
- Демон: `daemon_status`.

### Ресурсы
- `thzdaq://procedures` — каталог;
- `thzdaq://procedures/{name}` — описание и `guide`;
- `thzdaq://station` — профиль без секретов;
- `thzdaq://guide/{topic}` — методика из `docs/assistant/`.

### Транспорт и процесс
- stdio, отдельный процесс `thzdaq mcp`: Claude Code и Codex запускают его сами по
  `.mcp.json` / `~/.codex/config.toml`. Он вызывает `connect_or_start()` и работает как
  обычный клиент демона с origin `mcp:<имя клиента из initialize>`.
- MCP внутри демона (Streamable HTTP) не делаем: SDK построен на asyncio/ASGI, а демон — на
  потоках и stdlib. asyncio и зависимость `mcp` живут только в `thzdaq-mcp`.
- `RemoteLab` синхронный (stdlib `http.client`), поэтому вызовы оборачиваются в
  `anyio.to_thread.run_sync`. Иначе ожидание подтверждения или долгое чтение заблокирует
  цикл и сломает отмену.

### Долгие операции
- `start_measurement` сразу возвращает run id. `wait_measurement(id, timeout ≤ 60 с)`
  возвращает статус, прогресс и краткие результаты; агент вызывает его в цикле.
- Пока `wait_measurement` ждёт, прогресс уходит через MCP progress notifications (если
  клиент передал `progressToken`).
- `cancel_measurement` доступен всегда. Отмена MCP-запроса клиентом (`notifications/
  cancelled`) прерывает ожидание, но не само измерение.

### Подтверждения
- Кто отвечает: любой **человеческий** клиент — окно GUI (карточка) или CLI в интерактивном
  терминале (вопрос в терминале у того, кто вызвал). Агенты и скрипты отвечать на
  подтверждения не могут. Ответ первого ответившего закрывает запрос у остальных.
- Скрипт, запущенный без человека рядом (`thzdaq script start`), может заранее получить
  разрешения при запуске: `--allow set:sis_bias_1`, `--allow call:chopper_1`. Человек
  подтверждает их один раз при старте, и они записываются в метаданные измерения. Опасные
  действия (`danger`) заранее не разрешаются: они всегда требуют живого подтверждения.
- `ask` из политики и `ask_user` показываются карточкой в GUI. Вызов ждёт ответа до
  таймаута (по умолчанию 50 с, меньше таймаута инструмента у клиента), потом возвращает
  `pending` и id для `wait_answer`.
- Отказ возвращается как обычный результат с текстом человека («denied: сначала проверь
  накачку»), а не как ошибка протокола: модель должна его прочитать и учесть.
- MCP elicitation (вопрос через самого клиента) — только дополнительно, если клиент заявил
  поддержку. Опираемся на карточку в GUI.
- Нет ни одного человеческого клиента, который может ответить → операции с `ask` получают
  отказ «нужно подтверждение человека (откройте GUI)», а `ask_user` ждёт, пока GUI не
  подключится, или до таймаута.

### Ошибки и результаты
- Ошибки демона (лимит, неизвестное устройство, неверный параметр, отклонённый конфликт на
  `exclusive`) возвращаются как
  результат с `isError: true` и понятным текстом, что исправить, а не как исключение.
- Значения в ответах — с единицами показа (`2.3 mV`, `-45.1 dBm`). Можно передать единицы
  во вход (`"2.3mV"`); демон переводит в СИ тем же разбором, что и CLI.
- Ответы короткие: сводки, а не массивы. Полные данные — в файле измерения (путь в ответе).

### Подключение агентов
- `thzdaq mcp` — подкоманда CLI. Она работает, если установлен пакет `thzdaq-mcp`; иначе
  пишет, что его поставить. В сборке он уже есть.
- `.mcp.json` для Claude Code пишет `agent-setup` — абсолютный путь к тому CLI, который его
  вызвал:
  - из исходников:
    `{"mcpServers": {"thzdaq": {"command": "uv", "args": ["run", "thzdaq", "mcp"]}}}`;
  - из сборки: `{"command": "C:\\ThzDAQ\\thzdaq-cli.exe", "args": ["mcp"]}`;
  - из PyPI: путь к `thzdaq` в окружении.
- Пример `config.toml` для Codex — в `docs/assistant/agents.md`.
- `docs/assistant/agents.md`: как мерить через MCP и CLI, правила (не задавать значения вне
  рабочих диапазонов, сначала `describe_*`, долгие измерения через `wait_measurement`).

### Тесты
Клиент-сервер в памяти из SDK + демон в потоке на симуляторах:
- список инструментов совпадает с каталогом;
- вызов `start/wait` доходит до `completed`;
- отказ по лимиту; конфликт на `exclusive` → вопрос человеку, а `shared` → выполняется
  с записью в оба измерения;
- `ask` с ответом из «GUI» (тестовый клиент отвечает на `approval_requested`);
- прогресс приходит.

## Python-библиотека и свои скрипты

Цель: свой скрипт пишется просто, без лишнего кода. Он пользуется тем же демоном, его
измерение видно в GUI и в CLI (`thzdaq status`, `watch`, `cancel`), а команды библиотеки
совпадают с командами CLI.

### Два слоя одного клиента
- **Функции = команды CLI** (`thzdaq_api.lab`, поверх `RemoteLab`; реэкспорт в `thzdaq`):
  `lab.read(ref)`, `lab.set(ref, key, value)`, `lab.call(ref, action, **args)`,
  `lab.start(procedure, devices=..., **parameters)`, `lab.status()`, `lab.cancel(id)`,
  `lab.wait(id)`, `lab.measurements()`. Каждая — один вызов операции. CLI — тонкая обёртка
  над теми же функциями, поэтому имена и поведение совпадают.
- **Объекты устройств** — тонкая надстройка над функциями, около сотни строк:
  `lab["sis_bias_1"]` возвращает объект, атрибуты и методы которого строятся из
  `describe_device` (величины и действия):
  ```python
  from thzdaq import connect

  lab = connect()                      # найдёт или запустит демон
  bias, pm = lab["sis_bias_1"], lab["power_meter_1"]
  bias.voltage_set = "2.3mV"           # = lab.set(...) = thzdaq set sis_bias_1 voltage_set 2.3mV
  bias.read()                          # = thzdaq read sis_bias_1; словарь, значения в СИ
  pm.power                             # одна величина
  lab["chopper_1"].to_hot()            # действие
  ```
  Атрибут — это `__getattr__`/`__setattr__`, который вызывает `lab.read/set`. Своей логики у
  объектов нет, поэтому два стиля не дублируют друг друга, и тесты функций покрывают оба.
- Значения: чтение — float в СИ (для расчётов); запись — float в СИ или строка с единицей.
  `lab.read(ref, display=True)` — с единицами показа, как в CLI.

### Запуск встроенных процедур
```python
run = lab.run("sis.iv_curve", bias=bias, voltage="0:7:351")   # = thzdaq run ...
run.wait()                                                   # прогресс в stderr
iv = run.table("iv")                                         # колонки: voltage, current
```
Измерение идёт в демоне. В GUI в это время рисуется кривая, а `thzdaq status` его
показывает.

### Своё измерение — сессия из скрипта
```python
with lab.measurement("pv_fine", devices=[bias, pm], comment="узкий P-V") as m:
    m.plot("scan", x="voltage", y="power")         # живой график в GUI
    m.restore(bias, "voltage_set")                 # вернуть значение при любом завершении
    for v in m.sweep("2:3:51", unit="mV"):         # итератор сам проверяет отмену
        bias.voltage_set = v
        m.record("scan", voltage=v, power=pm.power)
        m.progress()
```
- Демон заводит обычное измерение (файл, номер, `procedure = "script:pv_fine"`, путь и хеш
  скрипта в метаданных) и регистрирует устройства сессии (раздел «Аренды и параллельные
  измерения»):
  - устройства из `devices=[...]` — `shared`; те, по которым скрипт делает развёртку,
    объявляются `exclusive=[bias]`;
  - устройство, которого нет в `devices`, добавляется само при первом обращении: при
    записи — как `shared`, при чтении — как `read`. Оно попадает в `devices` измерения, а в
    логе появляется подсказка объявить его явно. Скрипт не падает из-за забытого
    устройства;
  - `share=["sis_bias_1"]` — заранее согласиться на конфликт с чужим `exclusive`.
- `m.record` → события → живые графики в GUI по `m.plot` (спецификации графиков хранятся в
  метаданных измерения, как задумано в backlog для монитора); Data → Plot строит их потом
  так же.
- `thzdaq cancel <id>` из другого терминала, Stop в GUI или агент → событие скрипту →
  `m.sweep`/`m.check_cancel()` выбрасывают `Cancelled` → `with` закрывает измерение со
  статусом `cancelled`.
- `m.restore(device, key)` (вернуть значение) и `m.on_exit(device, action)` (вызвать
  действие, например `to_cold`) выполняет **демон**: при нормальном конце, при отмене и если
  скрипт умер
  (Ctrl+C, закрытый терминал — нет SSE и heartbeat дольше ~10 с). Измерение тогда
  `interrupted`, аренды снимаются, значения возвращаются через `GuardedPort`.
- Пределы, аренды и права те же, что у всех: origin `script:<имя>`.

### Где выполняется скрипт
- `python my_scan.py` — в своём терминале. Удобно для отладки и Jupyter. Если закрыть
  терминал, сработают `restore` и `interrupted`.
- `thzdaq script start my_scan.py [--python PATH] [-- args]` — скрипт запускает демон: тем
  же интерпретатором, что вызвал команду (или указанным), с переменной `THZDAQ_SCRIPT_ID`.
  Скрипт переживает закрытие терминала, вывод пишется в `<рабочая папка>/data/scripts/
  <id>.log`. Команды:
  - `thzdaq script list`;
  - `thzdaq script logs <id> [-f]`;
  - `thzdaq script stop <id>` — сначала отмена, через N с — завершение процесса.

  Скрипты видны в доке Daemon.
- Свои процедуры с формой в GUI (папка `procedures/`, демон загружает классы `Procedure`)
  — следующий шаг, после сессий скриптов.

### Формат данных сессии
Тот же файл, что у встроенных процедур: `data/<дата>/<id>_script_<имя>.json`, формат
`thzdaq-measurement` v1 (`data/measurement.py`). Отдельного формата нет: Data → Plot / Add
curve, экспорт CSV и `thzdaq show` работают как с любым измерением.

**Правило для сложных циклов:** одна таблица на один вид точки, а каждая переменная
вложенного цикла — это колонка. Вложенные циклы не превращаются во вложенные таблицы: таблица
остаётся плоской («длинной»), и любой срез потом делается фильтром по колонкам. Кривые на
графике разводятся `group_by`.

Пример: P-V hot/cold по углам сетки, с Y-фактором и Tn. Встроенная процедура `sis.pv_curve`
(`hot_cold` + `use_grid`) делает то же самое. Пример показывает, как это пишется скриптом,
чтобы потом менять под себя.
```python
from thzdaq import connect
from thzdaq_analysis.noise import match_hot_cold, noise_temperature  # thzdaq[analysis]

lab = connect()
bias, pm = lab["sis_bias_1"], lab["power_meter_1"]
load, grid = lab["chopper_1"], lab["grid_1"]
T_HOT, T_COLD = 300.0, 77.0

with lab.measurement(
    "pv_hot_cold_grid",
    devices=[bias, pm, load, grid],
    exclusive=[bias],                # развёртка по смещению: чужие изменения портят данные
    parameters={"bias": "0:7:351 mV", "angle": "0:90:10 deg", "t_hot": T_HOT, "t_cold": T_COLD},
    comment="P-V hot/cold по углам сетки",
) as m:
    m.plot("pv", x="voltage", y="power", group_by=("angle", "load"))           # P-V
    m.plot("y_factor", x="voltage", y="noise_temperature", group_by=("angle",))  # Tn-V
    m.restore(bias, "voltage_set")   # демон вернёт смещение при любом завершении
    m.restore(grid, "angle")
    m.on_exit(load, "to_cold")       # и поставит холодную нагрузку

    for angle in m.sweep("0:90:10", unit="deg"):    # проверяет отмену на каждом шаге
        grid.angle = angle
        m.sleep(1.0)                                # сетка доезжает
        sweeps = {}
        for state in ("hot", "cold"):
            getattr(load, f"to_{state}")()
            m.sleep(2.0)
            points = []
            for v in m.sweep("0:7:351", unit="mV"):
                bias.voltage_set = v
                m.sleep(0.01)
                r = bias.read()                     # напряжение и ток одним опросом
                p = pm.power
                m.record("pv", angle=angle, load=state, voltage_set=v,
                         voltage=r.voltage, current=r.current, power=p)
                points.append((r.voltage, p))
                m.progress()
            sweeps[state] = points
        for v, hot, cold in match_hot_cold(sweeps["hot"], sweeps["cold"]):
            m.record("y_factor", angle=angle, voltage=v, y_factor=hot - cold,
                     noise_temperature=noise_temperature(hot, cold, T_HOT, T_COLD))
```
Описывать колонки здесь не нужно:
- `voltage`, `current`, `power` приходят с приборов;
- `angle` и `voltage_set` — из развёрток;
- `y_factor`, `noise_temperature`, `load` есть в `KNOWN_COLUMNS`.

Переименовать колонку можно необязательным `m.columns(power=("IF power", "dBm"))`.

Что попадает в файл (сокращённо):
```json
{
  "format": "thzdaq-measurement", "version": 1,
  "id": 57, "procedure": "script:pv_hot_cold_grid", "status": "completed",
  "parameters": {"bias": "0:7:351 mV", "angle": "0:90:10 deg", "t_hot": 300.0, "t_cold": 77.0},
  "devices": {"sis_bias_1": {...}, "power_meter_1": {...}, "chopper_1": {...}, "grid_1": {...}},
  "tables": {
    "pv": {
      "columns": [
        {"key": "angle", "title": "Angle", "unit": "deg"},
        {"key": "load", "title": "Load", "unit": ""},
        {"key": "voltage_set", "title": "Voltage setpoint", "unit": "V"},
        {"key": "voltage", "title": "Voltage", "unit": "V", "source": "sis_bias_1/voltage"},
        {"key": "current", "title": "Current", "unit": "A", "source": "sis_bias_1/current"},
        {"key": "power", "title": "Power", "unit": "dBm", "source": "power_meter_1/power"}
      ],
      "data": {"angle": [0.0, 0.0, ...], "load": ["hot", "hot", ...],
               "voltage_set": [0.0, 2.0e-5, ...], "voltage": [...], "current": [...], "power": [...]}
    },
    "y_factor": {
      "columns": [{"key": "angle", ...}, {"key": "voltage", ...},
                  {"key": "y_factor", "title": "Y-factor", "unit": "dB"},
                  {"key": "noise_temperature", "title": "Noise temperature", "unit": "K"}],
      "data": {...}
    }
  },
  "station": {...},
  "metadata": {"script": {"path": "scripts/pv_hot_cold_grid.py", "sha256": "...", "text": "..."},
               "plots": [{"table": "pv", "x": "voltage", "y": "power", "group_by": ["angle", "load"]}, ...]}
}
```
- **Единицы и названия колонок (решено: автоматически, явное — по желанию).** Показания
  устройства (`pm.power`, `r.voltage`) и значения развёртки (`m.sweep(..., unit="mA")`) —
  числа с единицей, названием и источником (подкласс `float`: в расчётах ведёт себя как
  обычное число). Если колонку не описали, `m.record` берёт описание из значения сам.
  Необязательный `m.columns(...)` (или `columns=` в `lab.measurement`) переопределяет
  название и единицу любой колонки, в том числе пришедшей с прибора, и описывает
  посчитанные значения (`y`, `tn`). Посчитанное без описания получает название из ключа и
  пустую единицу, как сейчас для неизвестных ключей.
- В `Column` добавляется необязательное поле `source` (устройство/величина). Это
  совместимое расширение формата v1: старые файлы читаются, новые поля старой версией
  игнорируются.
- В `metadata` — путь, хеш и текст скрипта (воспроизводимость), а также спецификации
  графиков из `m.plot`, чтобы Data → Plot строил их потом так же.
- Значения хранятся в СИ, как везде. Трасса (массив) в ячейке допустима — это обычный
  список JSON.

### Долгие измерения на диске
Сейчас раннер каждые 5 с перезаписывает файл целиком. Для многочасового мониторинга (десятки
тысяч строк) это мегабайты каждые несколько секунд. Предлагаю для всех измерений:
- во время работы дописывать строки в соседний `<id>_<имя>.jsonl` (одна строка — одна
  запись, только добавление);
- JSON обновлять реже, а в конце собрать его целиком и удалить `.jsonl`;
- после сбоя читать JSON + хвост `.jsonl`: данные не теряются, статус `interrupted`.

### Живой график без GUI
Если GUI открыт, ничего делать не нужно: измерение скрипта или CLI появляется в нём, а
графики из `m.plot` выходят вперёд. Если GUI закрыт, есть несколько способов, и все они
подписываются на события демона, а не читают файл:
- **Окно графиков по запросу:** `thzdaq plot <id>` или в Python `m.show()` / `run.show()` /
  `lab.plot(id)`. Открывается лёгкое окно только с графиками этого измерения — тот же
  `graphs.py`, без доков и профиля (`thzdaq_gui.viewer`, у сборки `ThzDAQ.exe --plot <id>`).
  Можно указать свой график: `thzdaq plot 57 --table pv --x voltage --y power --group angle`.
  Нужен установленный `thzdaq-gui` или exe (путь берётся из файла хоста). Окно — отдельный
  процесс, скрипт не ждёт его закрытия.
- **В терминале (позже):** `thzdaq watch <id> --plot [--table … --x … --y …]` рисует график
  символами (plotext) и обновляет его на месте; без `--plot` — прогресс и последние строки.
  Удобно по ssh и для агентов.
- **В Jupyter (позже):** `run.live_plot()` / `m.live_plot()` — график в ячейке, обновляется по
  событиям (matplotlib или plotly — extra `thzdaq[jupyter]`).
- **Из `m.plot`:** `m.plot(..., show=True)` открывает окно сразу при старте, если GUI
  закрыт. По умолчанию окно не открывается.

### Сырые команды прибору
Для команд, которые драйвер пока не оборачивает. С осторожностью, только вручную:
- `thzdaq raw <instrument> "<команда>"`, `lab.raw(instrument, "<команда>")`, консоль в
  доке прибора (раздел Advanced, свёрнут).
- Идут через полосу прибора и блокировку линка, поэтому не мешают измерениям и опросу.
  Сырая запись в устройство, которое чужое измерение держит как `exclusive`, — конфликт с
  явным намерением, как у обычного set. Если устройство в режиме `shared` — запись в журнал
  обоих измерений.
- **Запросы** (команда с `?`): разрешены человеку и скриптам.
- **Запись:**
  - опасное действие: пределы и `GuardedPort` не проверяют сырую команду;
  - человек в GUI или CLI подтверждает (в CLI — `--yes` или вопрос в терминале);
  - скрипт — только если запущен с явным разрешением (`thzdaq script start --allow-raw`);
  - агентам и ассистенту сырая запись запрещена без вариантов, запросы — `ask`.
- Каждая сырая команда пишется в журнал с origin и ответом. После сырой записи состояние
  устройства в доках и кэше демона помечается «неизвестно» и перечитывается.
- Если команда нужна постоянно, её добавляют в драйвер как величину или действие.

## Рабочая папка

Рабочая папка — это папка эксперимента: где лежат данные, скрипты, настройки и файлы для
агентов. GUI и CLI работают в ней одинаково, поэтому можно мерить из терминала, а потом
открыть GUI в той же папке и продолжить.

### Что в ней
```
my-experiment/
  thzdaq.toml          # профиль стенда (имя в общем stations/), интерпретатор для скриптов, заметки
  data/2026-10-27/000042_sis_iv_curve.json
  data/scripts/<id>.log
  scripts/*.py         # свои скрипты
  stations/            # копии профиля, с которыми здесь мерили (история)
  AGENTS.md, CLAUDE.md, .mcp.json    # thzdaq agent-setup, по желанию
```
- Папка без `thzdaq.toml` — не рабочая. Рабочая папка по умолчанию — папка программы (её
  `data/`, `scripts/`), как сейчас. Существующие данные и сборки продолжают работать без
  изменений.

### Данные: у каждого клиента своя папка
- Измерение пишется в рабочую папку того, кто его запустил: CLI в папке A → `A/data`, GUI
  в папке B → `B/data`. Клиент передаёт папку с каждой операцией `start` / `measurement`;
  путь к файлу фиксируется при старте измерения и дальше не меняется.
- Демон держит `MeasurementStore` на каждую папку (`application/workspaces.py`, сделано).
  Номер — наибольший в папке + 1, но не меньше последнего номера демона: «#42» однозначно
  называет идущее измерение, его аренды и события. В папке номера растут, но могут идти с
  пропусками.
- GUI видит все идущие измерения стенда (один демон), но в Data по умолчанию показывает
  измерения своей папки. Чужие помечены («из `A`»), их можно показать фильтром.
- Аренды, пределы и права — общие для стенда и от папки не зависят.

### Профиль стенда: общий + копия в папке
- Рабочий профиль один — в общем `stations/` программы (адреса, пределы, устройства). Его
  использует демон, правится он в Setup.
- В рабочую папку кладётся копия для истории: при старте измерения, если профиль
  изменился с последней копии, демон сохраняет `stations/<имя>@<дата-время>.yaml` в эту
  папку. В измерении записывается ссылка на копию и её хеш (вдобавок к снимку стенда,
  который уже есть в каждом файле).
- `thzdaq.toml` хранит, какой профиль ожидает папка. Если демон работает с другим
  профилем, клиент предупреждает и предлагает переключить — по общему правилу
  «несовпадение профиля», с запретом на время идущих измерений.

### GUI
- При запуске: недавние рабочие папки, «Открыть папку…», «Новая рабочая папка…»
  (создаёт `thzdaq.toml`, `data/`, `scripts/`, по желанию файлы для агентов). Последняя
  папка открывается сама; список недавних — в QSettings.
- Меню File:
  - Open workspace, Recent;
  - Open in VS Code (`code <папка>`, если `code` есть в PATH; иначе выбранный в
    настройках редактор);
  - Open in Explorer.
- Заголовок окна показывает папку.
- Несколько окон GUI в разных папках одновременно — это просто несколько клиентов
  демона.

### CLI
- Рабочая папка ищется от текущего каталога вверх до `thzdaq.toml` (как git). Не нашлась
  — папка программы по умолчанию. `--workspace PATH` задаёт явно.
- `thzdaq init [--agents]` создаёт рабочую папку в текущем каталоге.
- `thzdaq gui` открывает GUI в рабочей папке текущего каталога; если GUI уже открыт в
  другой папке, открывается второе окно.

### Интерпретатор для скриптов
- **CLI:** `python my.py` и `thzdaq script start` используют тот Python, где установлен
  `thzdaq`; `--python PATH` — другой.
- **GUI:** по умолчанию встроенный Python сборки (`thzdaq-cli.exe run-script file.py`,
  консольный exe, поэтому `print` и traceback попадают в вывод): stdlib, numpy, thzdaq —
  работает без установки чего-либо. В настройках рабочей папки
  (`thzdaq.toml`) можно выбрать другой: `.venv` папки, окружение uv или conda, любой путь.
  GUI показывает найденные окружения и проверяет, что в выбранном установлен
  `thzdaq` совместимой версии.
- **Сборка:** PyInstaller кладёт в exe только найденные модули. Для скриптов на встроенном
  Python в сборку включается стандартная библиотека целиком, иначе скрипт упадёт на
  `import statistics`. Тяжёлое (scipy и т. п.) — через своё окружение.

## Редактор скриптов в GUI

Док **Scripts**: слева список скриптов рабочей папки (`scripts/` и добавленные папки),
справа редактор, снизу вывод. Скрипт — обычный `.py`-файл на диске, поэтому его же
редактируют VS Code, Claude Code или Codex.

### Редактор
- `QPlainTextEdit`:
  - номера строк;
  - подсветка через pygments;
  - автодополнение через jedi (Python и API `thzdaq_core`);
  - наши подсказки: имена устройств стенда в `lab["…"]`, величины и действия устройства
    после точки (из `describe_device`), имена процедур и их параметры.
- Проверка при сохранении и по Check:
  - pyflakes — синтаксис и неизвестные имена;
  - наша проверка — устройство или величина не существует на стенде, значение в
    `m.sweep` вне пределов `safety`.
- Новые скрипты — из шаблонов: развёртка, карта 2D, hot/cold, монитор, запуск процедуры с
  обработкой.
- Data → «Скрипт этого измерения» открывает текст из метаданных (как был при запуске) в
  редакторе; его можно сохранить и запустить снова.

### Запуск
- Run = `thzdaq script start` с интерпретатором рабочей папки. Вывод идёт в панель по
  событиям демона, а измерения скрипта появляются в Data и на графиках как обычно.
- Stop = отмена (`m.sweep` выходит, `restore` выполняется), через N с — завершение
  процесса.
- Ошибка — traceback в панели со ссылкой на строку.
- Несохранённый скрипт перед запуском сохраняется: демон запускает файл с диска, и в
  измерение попадает именно его текст.

### Правки ассистента и внешних агентов
- Встроенный ассистент видит:
  - открытый скрипт, выделение и курсор;
  - ошибки проверки;
  - вывод и traceback последнего запуска.

  Инструменты: `script_list`, `script_read`, `script_propose_edit`, `script_run` (с
  подтверждением), `script_stop`, `script_logs`, `editor_state`. Те же операции есть у
  MCP-агентов.
- **Правка выглядит как в VS Code.** Изменённые куски подсвечиваются прямо в тексте:
  удалённые строки красным (зачёркнуты, только для чтения), добавленные зелёным. У каждого
  куска:
  - ✓ — принять;
  - ✗ — отклонить;
  - «Переделать» с полем ввода — комментарий уходит ассистенту, и он присылает новую
    правку.

  Вверху — «Принять всё» и «Отклонить всё». Пока есть непринятые куски, правка текста
  вручную заблокирована. Куски считаются через difflib.
- **Правки с диска** (Claude Code, Codex, VS Code): `QFileSystemWatcher` замечает
  изменение файла.
  - Несохранённых правок в редакторе нет → текст обновляется, и изменения показываются так
    же, кусками с ✓ (оставить) / ✗ (откатить), с пометкой «изменено снаружи».
  - Есть несохранённые правки → баннер конфликта: «перезагрузить», «оставить моё» или
    «сравнить».
- Запуск скрипта агентом — всегда через подтверждение (класс прав `run`), независимо от
  того, кто правил текст.

## Скрипт → виджет измерения (подумать позже)

Сейчас не обязательно, но направление нужно держать в голове, чтобы API скриптов ему не
мешал. Встроенные измерения захардкожены и отлажены; хочется, чтобы своё измерение из скрипта
тоже можно было превратить в док с формой параметров, выбором устройств, Start/Stop и
графиками, сохранить и запускать из GUI, как встроенные.

### Путь созревания
1. **Скрипт** — как в примере выше: значения прямо в коде.
2. **Скрипт с объявленными параметрами и слотами** — GUI строит по ним форму, а
   `thzdaq script start` принимает `--set` / `--device`, как `thzdaq run`.
3. **Сохранённое своё измерение** — пункт в Measures → Custom, свой док, последние значения
   запоминаются, как у встроенных.
4. **Встроенная процедура** — если измерение прижилось, его переносят в
   `measurements/procedures/` с тестами на симуляторах.

### Как могло бы выглядеть объявление
Параметры, слоты и графики объявляются так же, как у `Procedure`. Демон описывает такой
скрипт тем же `ProcedureInfo`, и GUI строит форму, слоты и запуск тем же кодом, что для
встроенных процедур. Скрипт — клиент, поэтому возможности указываются по имени, а демон
проверяет имена.
```python
from thzdaq.script import Script, Sweep, Float, Slot, Plot

class PVGrid(Script):
    title = "P-V hot/cold по сетке"
    devices = {
        "bias": Slot("VoltageSource", "VoltageCurrentMeter", kind="sis_bias"),
        "detector": Slot("PowerDetector"),
        "load": Slot("LoadSwitch"),
        "grid": Slot("Rotator"),
    }
    bias_voltage = Sweep("Bias voltage", default="0:7:351", unit="mV")
    angle = Sweep("Grid angle", default="0:90:10", unit="deg")
    t_hot = Float("Hot load", default=300, unit="K")
    t_cold = Float("Cold load", default=77, unit="K")
    plots = [Plot("pv", x="voltage", y="power", group_by=("angle", "load"))]

    def run(self, m, d):     # m — сессия, d — устройства по слотам
        for angle in m.sweep(self.angle):
            ...              # тело как в примере, значения — из self.*
```
- Файл импортируется без запуска измерения: на верхнем уровне только объявления, а
  проверка в редакторе предупреждает о вызовах приборов вне `run`. Форма строится из класса.
- Запуск из дока = `thzdaq script start pv_grid.py --set ... --device ...`: скрипт так же
  выполняется своим процессом с выбранным интерпретатором, а пределы, аренды и `restore`
  работают как у любой сессии.
- Встроенные процедуры и такие скрипты различаются только тем, где идёт цикл: процедура —
  в демоне, скрипт — в своём процессе.

### Открытые вопросы
- Где хранить сохранённые измерения: в рабочей папке (`scripts/`) или общие для стенда
  (рядом с `stations/`), и как делиться ими между папками.
- Нужно ли выполнять такие измерения внутри демона (папка `procedures/`), а не своим
  процессом, ради скорости и независимости от клиента.
- Версии: измерение, сохранённое как виджет, со временем меняется. Текст скрипта и так
  кладётся в каждое измерение, но нужно ли хранить историю самого виджета.
- Хватит ли автоматической формы, или понадобится своя раскладка (группы, условные поля,
  как `hot_cold` → слот `load` у P-V).

## Пакеты на PyPI
- Внутри — отдельные пакеты («Пакеты, слои и границы»), а человек ставит одно имя `thzdaq`:
  - `uv tool install thzdaq` — команда `thzdaq` глобально; клиент без драйверов и numpy;
  - `uv add thzdaq` / `pip install thzdaq==<версия exe>` — в свой проект, Jupyter или conda:
    `from thzdaq import connect`;
  - `thzdaq[analysis]` — функции анализа для своих расчётов в скрипте (thzdaq-analysis,
    только numpy);
  - `thzdaq[daemon]` — демон с драйверами: стенд на чистом Python без exe (Linux, своё
    окружение);
  - `thzdaq[mcp]` — `thzdaq mcp` для агентов;
  - `thzdaq[gui]` — окно; `thzdaq[jupyter]` — живые графики в ячейке (позже); `thzdaq[all]` —
    всё.
- API только localhost, поэтому клиенту без `[daemon]` демон нужен на этой же машине:
  `connect_or_start()` подключается к запущенному или запускает установленную сборку (путь —
  из файла установки пользователя). Нет ни демона, ни сборки — ошибка называет, что
  поставить.
- Тот же workflow релиза по тегу публикует все пакеты (trusted publishing из GitHub Actions)
  вместе со сборкой exe. Версия у всех пакетов одна — версия программы, её ставит
  `release.py`.
- На ПК стенда со сборкой ставить ничего не нужно: там уже есть `thzdaq-cli.exe` (CLI, MCP,
  встроенный Python для скриптов). PyPI нужен для своих окружений (Jupyter, scipy, другой
  проект).
- Совместимость: клиент и демон сверяют `api_version`. Один major — работают; иначе ошибка
  называет версию, которую надо поставить.
- Проверить: свободны ли имена на PyPI (`thzdaq`, `thzdaq-*`). `numpy<2` остаётся только у
  thzdaq-core и к клиенту не попадает.
- Python ≥ 3.11.

## Агенты рядом с GUI (Claude Code, Codex)
Сценарий: человек работает в GUI, рядом в терминале или в приложении открыт Claude Code
или Codex.
- `thzdaq agent-setup [<рабочая папка>]` (или `thzdaq init --agents`, или галочка при
  создании рабочей папки в GUI) кладёт в рабочую папку файлы для агента. Агент работает в
  той же папке, что и GUI, видит её `scripts/` и `data/`:
  - `AGENTS.md` (и `CLAUDE.md` со ссылкой на него) — что такое ThzDAQ, правила (пределы,
    опасные действия, единицы), как мерить через MCP и когда писать скрипт на клиенте;
  - `.mcp.json` для Claude Code;
  - пример блока для `~/.codex/config.toml`. Проверить, поддерживает ли Codex конфиг на
    уровне проекта.
- Пользователь пишет агенту: «сними I-V на sis_bias_1 и найди щель».
  1. Агент вызывает MCP-инструменты, а для длинной логики пишет скрипт на клиенте и
     запускает его через `thzdaq script start`.
  2. Всё выполняет демон.
  3. В GUI видны доки, графики, карточки подтверждений и подсветка, если агент её
     запросил.
- Агенты работают по своей подписке, ключ API не нужен. ThzDAQ их логин не трогает.

## Ассистент в GUI: как он понимает инструменты
Механизм тот же, что у MCP: **инструмент — это имя, описание и JSON-схема аргументов**.
MCP лишь передаёт этот список чужой программе; внутри GUI он передаётся модели напрямую.
- **Каталог операций** (`thzdaq_api.catalog`) — описание для модели, схема, класс прав,
  флаг «долгая», флаг `danger`. Из него строятся `tools` для модели, инструменты MCP и
  справка CLI.
- **Цикл:**
  1. запрос к модели (OpenAI-совместимый `chat/completions`) с `tools=[...]`;
  2. модель отвечает текстом или `tool_calls`;
  3. каждый вызов выполняется через `RemoteLab` GUI с origin `assistant`: права,
     пределы, карточка подтверждения;
  4. результат возвращается модели сообщением `role: tool`;
  5. повтор, пока модель не ответит текстом.

  Лимит шагов на одно сообщение пользователя; Stop прерывает цикл.
- **Системный промпт** собирается при каждом разговоре и обновляется при изменении стенда:
  - роль и правила (единицы, пределы, опасные действия, «сначала describe»);
  - устройства с возможностями и статусом соединений;
  - краткий каталог процедур (имя, что меряет, слоты);
  - методика из `docs/assistant/`.

  Подробности модель запрашивает инструментами (`describe_procedure`, `describe_device`).
- В чате каждый вызов — свёрнутая карточка («set_quantity sis_bias_1 voltage_set 2.3 mV →
  ok»).
- Модели нужен вызов функций. «Test» в диалоге провайдеров проверяет и связь, и то, что
  сервер принимает `tools` (у vLLM — флаги `--enable-auto-tool-choice` и парсер для Qwen).
- Чат и ключи — в GUI (ключ в `keyring`). Измерения, запущенные ассистентом, идут в демоне
  и продолжаются после закрытия GUI. Сам разговор при этом заканчивается.

  - `host.py` — файлы демона, папка программы, `connect_or_start()`, отвязанный запуск,
    `kill`; файл установки — со сборкой (шаг 8);
  - `script.py` — сессии скриптов на стороне клиента (`lab.measurement`, `m.sweep`,
    `m.record`, `m.plot`).

  только numpy.
- `thzdaq-instruments`: `actions.py` — `Action`, `Argument` и вывод действий из возможностей
  рядом с `quantities.py`; `actions` у драйверов (чоппер; дальше sumitomo, rs); `limits.py` —
  `Limit`, паспортные `limits` / `channel_limits` у драйверов; `Quantity.setters` и `danger`;
  `parse_as` проверяет `minimum/maximum`; возможность `OutputProtection`;

  соединения.

  - `domain/station/` — профиль (`config`, `kinds`, `safety`: `SafetyLimit`, `Safety`,

    уставок; дальше проверка после записи);
  - `domain/measurements/` — `Procedure`, параметры (`applies`), `slot_modes` (по умолчанию
    `shared`; у встроенных процедур `exclusive` для слотов развёртки, у `monitor.time` все

  - `application/dispatch.py` (диспетчер и конвейер), `policy.py`, `approvals.py`
    (подтверждения, ответ от любого человеческого клиента, заранее выданные разрешения
    скриптов);
  - `application/handlers/<область>.py` — обработчик на операцию, `assembly.py` — явный
